2.9.1 What a kit is

A kit is the bridge layer. It connects Squared to an external system, and that system to the platform:

Squared Application
        v
Squared Framework
        v
Kit  (bridge)
        v
External Framework   (SDL3, SFML, ncurses)
        v
Platform             (Android, Linux, terminal)

This is the chain described in the project vision: Squared talks to SDL3 through a bridge, and SDL3 to Android.

A kit MAY provide adapters, framework bridges, platform integration, initialization and lifecycle code, event/input/rendering translation, build configuration fragments, dependency declarations, platform-specific sources, kit resources, and compatibility metadata.

A kit MUST integrate through documented Squared public interfaces and MUST NOT modify Squared framework internals. A kit MUST NOT define the overall project structure — that is the template's role — and MUST NOT assume it owns the workspace.

The external framework itself remains an external dependency, conceptually distinct from the kit that bridges it.

2.9.2 Kit manifest block

A kit's declarations live under consumers.squared_pg (cartridge format §5.6). As with templates (§2.8.6), this section is the only normative definition of the schema and nothing validates it.

"consumers": {
  "squared_pg": {
    "external": {
      "id": "sfml",
      "version": ">=3.0.0",
      "acquisition": "system"
    },

    "runtime": { "model": "polled" },

    "platforms": ["linux", "android"],
    "compatible_templates": ["template.terminal.cpp"],
    "integration_areas": ["render.backend"],
    "conflicts_with": ["kit.sdl3"],
    "provides": ["graphics", "input"],

    "requires": {
      "engine":    ">=0.1.0 <0.2.0",
      "framework": ">=1.0.0 <2.0.0",
      "packages":  []
    },

    "ownership": {
      "generated": ["sq_kit/**"],
      "default":   "generated"
    }
  }
}

Field names corrected against the implementation

Version 1.0 of this section named six members that no implementation has ever read:

This section saidThe engine reads
supported_templatescompatible_templates
supported_platformsplatforms
supported_frameworkrequires.framework
requires_packagesrequires.packages

A kit written to the old text would have resolved as though it declared nothing: unconstrained platforms, every template compatible, no integration areas. It would not have failed — §2.8.6's fallback rule would have absorbed every one of those names as absent — which is exactly the failure mode a normative document is supposed to prevent, and why the divergence went unnoticed until this section was checked against the code.

files and migrations are removed rather than corrected. Per-file ownership is ownership (§2.7.10), and migrations belong to the regeneration path §2.7.11 defers.

runtime.model

Declares which side of the kit's main loop calls the other: none (the kit contributes no loop), polled (the application drives the kit), callback (the kit's runtime drives the application).

Nothing reads it. It was added during the cartridge format 2.0 bump against a kit.sfml that does not exist, and every shipped kit declares none. It is recorded here as reserved so an author who copies it knows it currently does nothing.

2.9.3 Integration points

An integration point is a named anchor a template declares ([[2.8 Templates]] §2.8.6) that kits and packages may contribute to. Points are named, not positional, so contributions are comparable without inspecting file content.

Rules:

  • A kit MUST declare every integration point it writes.
  • A kit MUST NOT write to a point the active template does not declare.
  • Two kits writing the same point MUST both declare it; whether that is a conflict is determined by the point's declared arity.

Point arity, declared by the template:

ArityMeaning
singleexactly one contributor; a second is a conflict
multimany contributors; contributions are emitted in resolution order

Conflicts MUST be detected during cross-validation, before any workspace mutation, and reported as a structured compatibility error. Lua then removes a kit, selects an alternative, amends the workflow, or terminates.

conflicts_with declares a known incompatibility independent of integration points, and MUST be honoured even if no point collides.

Who owns an integration point's substrate

An integration point has two parts: the substrate that makes the point exist at all, and the filling a kit contributes to it.

The substrate belongs to whoever cannot be absent. A template is always present; a kit is optional by construction. So anything the workspace needs in order to build without a given kit belongs to the template, even when it looks like that kit's concern.

The concrete case: NDK detection and native_app_glue belong to template.android.cpp, not to kit.opengl. The template promises a workspace that builds and runs with no rendering kit at all — a NativeActivity that opens a window and does nothing is still a working Android application. If the glue arrived with the rendering kit, that promise would be false, and removing the kit would break the build in a way the template's own tests could not see.

The rule generalises: if removing a kit would leave the workspace unable to build, the thing that broke was never the kit's to provide.

A kit contributes to a host toolchain; it does not reorganise one

A kit adds to the build configuration of a workspace that already builds. It MUST NOT reorder, replace or take ownership of the host toolchain's existing search paths.

Two corrections stand as evidence, both found by on-device build failure rather than by review:

Additional sysroots are added with -idirafter, never -I. -I prepends, so an NDK sysroot added that way displaces the host's own C headers and libc++ stops finding them. -idirafter appends, so the sysroot serves only the headers nothing else provides. The failure is not a missing header; it is the wrong header found first, which surfaces far from its cause.

Libraries are named by path, not by -l with an added -L. An added -L changes resolution for every -l in the link, including ones the kit knows nothing about. Naming the file directly affects exactly the library intended.

The general rule: a kit's contribution must be additive and order-insensitive. If it only works when it comes first, it is reorganising the toolchain rather than adding to it.

2.9.4 External framework acquisition

external.acquisition declares how the external framework reaches the generated project:

ValueMeaning
packagesupplied by a named generator package (offline)
systemexpected to be present on the build host
vendoredvendored into the generated project by the kit

A kit using system MUST declare the detection mechanism the generated build will use, so the generated project can find the dependency without the generator.

Offline generation MUST be possible for every kit whose acquisition is package or vendored. A system kit MAY require host software at build time, but MUST NOT require network access at generation time.

2.9.5 Dependencies

Kits MAY depend on packages, other kits, and platform components. All dependencies MUST be declared in the manifest and MUST NOT be discovered through filesystem convention.

The engine MUST validate the complete kit dependency graph before application. The graph MUST be acyclic.

2.9.6 Composition

Multiple kits MAY be applied where compatibility permits:

template.android.cpp
    +-- kit.android
    +-- kit.sdl3

Composition MUST be deterministic. Application order is the resolution order of the kit set, which is itself deterministic ([[2.8 Templates]] §2.8.2).

2.9.7 Ownership and updates

Kit-contributed paths declare an ownership class exactly as template paths do ([[2.7 Project generation model]] §2.7.10). The generator MUST NOT overwrite a user-authored file merely because a kit originally provided a file at that path.

Kit versions MUST be recorded in workspace metadata. A kit update MUST NOT silently alter an existing project; updates occur only through the explicit workflow in §2.7.11.

Where a version change requires more than file replacement — moved paths, renamed targets, changed configuration — the kit MUST declare migrations. A required migration that is unavailable MUST fail the update rather than proceeding partially.

2.9.8 Validation

Before application a kit MUST be validated for: envelope and type block correctness, template compatibility, framework version compatibility, package requirements, platform requirements, dependency availability, integration point declarations, conflict declarations, and required parameters.

An invalid kit MUST NOT partially modify the workspace.
