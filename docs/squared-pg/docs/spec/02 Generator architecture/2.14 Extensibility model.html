2.14 Extensibility model

[!info] Navigation Index: [[Specification Index]] · Parent: [[2 Generator architecture]] Prev: [[2.13 Dependency graph]] · Next: [[2.15 Error and transaction model]]

Purpose

Defines how squared-pg is extended without modifying core generator code — the mechanism behind the vision's requirement that the Lua layer remain programmable after release, and that the generator be embeddable in other tools.

2.14.1 Engine capability tokens

[!note] Resolution of Q-05 (D-023), amended by D-053 This is the registry that gives a resource's capability requirements meaning. The original note said four manifest types declare requires_capabilities as a cartridge envelope field; that stopped being true when cartridge format 2.0 trimmed the envelope. See §2.14.1.1.

A capability token is a named, versioned engine feature.

capability.template.substitute@1.0
capability.archive.zip@1.0
capability.asset.transform.texture.compress.etc2@1.0
capability.build.emit.cmake@1.2
capability.build.emit.gradle@1.0

Rules:

  • Tokens follow the identifier grammar of [[2.8 Templates]] §2.8.1 with the type capability, and are versioned as SemVer.
  • The capability set is compiled into the engine and MUST be enumerable through the control surface.
  • Extensions MAY register additional tokens at initialization; they MUST NOT redefine an existing one.
  • A resource declaring capability requirements is satisfied when every token is present at a version satisfying its constraint.
  • Unsatisfied requirements MUST fail at resolution, never at materialization. The workflow must learn it cannot proceed before anything is written.

2.14.1.1 How a resource demands a capability

A resource declares its requirements in its own consumer section (§2.8.6, §2.9.2):

"consumers": {
  "squared_pg": {
    "requires": { "capabilities": ["capability.project.plan@^1.0"] }
  }
}

Each entry is name or name@range. A bare name is satisfied by any version.

Nothing validates the token's grammar before the engine sees it. Cartridge format 2.0 carries the consumer section as opaque text (§5.6), so a malformed token arrives here rather than being refused at open. That is correct: this engine owns the capability. namespace and is the only party that can say which capability is missing and what provides it. A container reader could only ever have said that a string it did not understand looked wrong.

2.14.1.2 requires_features is a different thing

The cartridge envelope retains requires_features, and the contrast is the reason it does:

GuardsDeclared inFails
requires_featuresthe readerthe cartridge envelopeat open(), before anything else
requires.capabilitiesthe consumerthe consumer sectionat resolution

A cartridge whose reader is too old cannot be opened at all — it may use a compression method or a signature scheme the reader does not implement, and only the container format can define what a reader must provide.

A cartridge whose consumer is too old opens perfectly well and must be refused later, by that consumer, for reasons the container format has no opinion about.

Stated as a rule: a newer sqcart satisfies requires_features; a newer generator satisfies requires.capabilities. They are not alternatives and a resource may need both.

Capability versions are part of the public contract. Removing or narrowing a capability is a breaking change and MUST be documented.

2.14.2 Extension services

Extension services expand engine functionality without modifying the core. They MAY provide additional template processors, package providers, platform integrations, validation systems, resource handlers, asset transformers, or build emitters.

An extension service MUST declare its identity, version, compatibility requirements, the capability tokens it provides, and the ones it requires. It MUST expose explicit APIs, follow engine ownership rules, and register through the controlled mechanism.

An extension service MUST NOT replace or modify a core service. A core service is part of the engine's contract; an extension that could swap one out would make that contract unverifiable. Extensions add; they do not substitute.

A missing optional extension MUST be reported but MUST NOT prevent operation unless an active workflow requires a capability only it provides.

Extensions participate in the shutdown lifecycle ([[2.4 Engine lifecycle]] §2.4.9) and MUST NOT prevent core cleanup.

2.14.3 Lua workflow discovery

[!note] Resolution of Q-16, part 1 (D-016)

Workflows are discovered from an ordered search path:

1. repository       lua/workflows/
2. user config      $XDG_CONFIG_HOME/squared-pg/workflows/
3. project-local    <workspace>/.squared/workflows/
4. explicit         paths supplied by the host or CLI

Each workflow directory contains workflow.json declaring:

{
  "schema_version": 1,
  "id": "workflow.generate.android",
  "version": "1.0.0",
  "entry": "init.lua",
  "requires_engine": "^1.0",
  "requires_capabilities": ["capability.build.emit.gradle@^1.0"],
  "trust": "sandboxed"
}

Discovery is deterministic: search paths in declared order, entries within a path sorted. A later path MAY shadow an earlier identity only when the host explicitly enables shadowing; otherwise a duplicate identity is an error.

Workflow capability requirements are checked at load, so a workflow that cannot run fails before it starts rather than midway.

2.14.4 Trust model

[!note] Resolution of Q-16, part 2 (D-016)

Two tiers:

trusted — the repository's own workflows and workflows in the user's configuration directory. Full Lua 5.4 standard library. These are the user's own code, on the user's own machine.

sandboxed — everything else, including project-local workflows and anything obtained from a third party. Default for any workflow that does not declare otherwise, and the only tier a host may grant to downloaded content.

Sandboxed workflows run without:

  • os.execute, os.remove, os.rename, os.tmpname
  • package.loadlib and C module loading
  • the debug library
  • raw io write access
  • load/loadstring over arbitrary strings

Sandboxed workflows reach the filesystem only through engine services, which is where provenance, validation, and transactions already live. They may read declared input paths supplied by the host.

A workflow MUST NOT elevate its own trust tier. Trust is assigned by the host, not claimed by the workflow — a trust field in workflow.json is a request, and the host MAY refuse it.

2.14.5 Custom resources

Users MAY author custom templates, kits, packages, and assets. A custom resource is an ordinary resource: same manifest envelope, same identity grammar, same validation. It is placed on a resource search path and indexed like any other.

Custom resources SHOULD use a vendor segment (kit.acme.raylib) and MUST NOT use a reserved namespace ([[2.8 Templates]] §2.8.1).

Nothing about authoring a custom resource requires modifying the engine. If it does, that is a defect in the resource model, not a reason to modify the engine.

2.14.6 Compatibility and versioning

Extensions declare an engine version constraint and capability constraints. The engine MUST refuse to load an extension whose constraints it cannot satisfy, and MUST report why.

Breaking changes to the capability set, the manifest schema, the operation registry, or the binding surface are compatibility changes and MUST be documented with a migration path ([[2.6 Engine-Lua boundary]] §2.6.15).

2.14.7 Prohibitions

An extension MUST NOT:

  • replace or modify a core service;
  • bypass the resource index, validation, or the transaction system;
  • write to a workspace except through engine services;
  • register a capability token that already exists;
  • elevate its own trust tier;
  • require network access in the core generation path;
  • introduce non-determinism into resolution.
