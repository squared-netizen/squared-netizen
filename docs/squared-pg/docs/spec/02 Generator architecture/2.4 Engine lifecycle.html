2.4.1 Engine creation

The engine MUST be an explicit runtime object with a well-defined ownership boundary. The instance represents the active squared-pg execution environment.

Creation MUST:

  • allocate the engine instance;
  • initialize internal state containers;
  • establish default configuration state;
  • prepare service registration;
  • prepare resource management;
  • prepare error reporting.

Creation MUST NOT parse arguments, read user configuration, select resources, generate files, modify the filesystem, or execute workflows.

The component creating the engine MUST also be responsible for initiating shutdown, directly or through a controlled ownership mechanism.

Implementation note: the engine instance is created through a factory returning std::unique_ptr; there is no global instance and no singleton.

2.4.2 Initialization sequence

Initialization is explicit and separate from creation. It MUST be deterministic: given the same configuration, resource set, and dependency versions, it MUST produce the same runtime state.

Order:

  1. Validate engine startup configuration.
  2. Initialize internal subsystems.
  3. Register engine services.
  4. Build the resource index.
  5. Initialize Squared project model support.
  6. Initialize template, kit, package, and asset systems.
  7. Expose the control surface.
  8. Mark the engine Ready.

Initialization MUST NOT select a template, modify a project directory, apply a kit, install packages, materialize assets, or execute workflow logic.

If initialization fails the engine MUST NOT enter the operational state, and MUST remain in a state where cleanup can be performed safely.

2.4.3 Service registration

Services are the capabilities exposed by the control surface. Each MUST have a well-defined API with explicit ownership, lifecycle, and error behaviour.

Core services, all registered during initialization:

ServiceResponsibility
Filesystemcontrolled filesystem operations, workspace management
Resourcediscovery, indexing, manifest loading, integrity
Templatetemplate resolution, validation, instantiation
Kitkit resolution, compatibility, integration
Packagepackage resolution, dependency graph, materialization
Assetasset indexing, resolution, transformation, materialization
ProjectSquaredProject model creation and management
Validationconfiguration, resource, and workspace validation
Transactionstaging, journaling, commit, rollback, recovery
Metadataworkspace metadata and provenance

A missing required core service MUST prevent the engine from entering Ready.

Extension services are optional and are defined in [[2.14 Extensibility model]]. A missing optional extension MUST be reported but MUST NOT prevent operation unless an active workflow requires it.

Service registration MUST be deterministic. The registry MUST remain independent from Lua workflow logic: Lua selects and sequences services, it does not define them.

Pattern: Service Locator, scoped to the engine instance rather than global.

2.4.4 Resource loading

[!note] Resolution of Q-11 (D-011) Initialization builds an immutable resource index mapping identity to manifest, version, and location. Lazy loading may only fetch payloads for already-indexed identities. The index MUST NOT change during a session.

Eager, at initialization:

  • resource discovery and indexing;
  • manifest loading and envelope validation;
  • identity, version, dependency, and compatibility metadata;
  • integrity information.

Lazy, on demand:

  • template file trees;
  • package contents;
  • asset payloads;
  • archives;
  • platform-specific resources.

This is what makes hybrid loading deterministic: the set of resources is fixed at initialization; only payload retrieval is deferred. A resource failure discovered during lazy loading MUST be reported through the same error system as an initialization failure.

[!note] Resolution of Q-12 (D-012) The Resource Service validates the manifest envelope — well-formedness, identity syntax, version syntax, integrity. The owning typed service validates the type block — what a template, kit, package, or asset manifest means.

Resource identity is manifest-based. Filesystem paths are never canonical identity:

template.android.cpp                 (identity)
resources/templates/android-cpp/     (implementation detail)

Lua MAY request resources by identity. Lua MUST NOT scan resource directories, modify manifests, bypass validation, or access internal resource storage.

Development repositories MAY use predictable layouts for maintainer convenience, but those layouts MUST NOT become part of the public contract.

2.4.5 API exposure

The control surface has two layers.

Service layer — low-level reusable capabilities. This is the fundamental control surface.

Operation layer — named, coordinated actions built from services.

[!note] Resolution of Q-08 (D-008) Operations MUST be documented compositions of service calls. No capability may exist only at the operation layer. The operation layer exists for convenience, consistency, and reduced boilerplate — never as a second source of truth.

Service APIs MUST have documented contracts, defined ownership and lifetime rules, deterministic behaviour, and structured error reporting.

Lua workflows MAY use either level:

-- service level
local template = engine.template.resolve("template.android.cpp")
local kit      = engine.kit.resolve("kit.sdl3")
local project  = engine.project.create(config)

-- operation level
local result = engine.project.generate(config)

The choice of abstraction belongs to the workflow author.

The API boundary MUST prevent direct access to internal engine state. Internal implementation details remain private unless intentionally promoted.

2.4.6 Operation execution

[!note] Resolution of Q-07 and Q-09 (D-007, D-009) The earlier draft carried two competing models. Unified here: execution is synchronous, and a typed C++ operation registry is canonical. The Lua table form is binding sugar over that registry. An optional job wrapper MAY exist but MUST NOT change the contract.

Registry

Every operation is registered with:

  • operation identity (a stable dotted name, e.g. project.generate);
  • a typed parameter structure;
  • a typed result structure;
  • required services;
  • required engine capabilities;
  • transaction requirements;
  • possible error codes.

The registry is compiled in and enumerable through the control surface, which is what allows Lua, tooling, and documentation generation to discover operations without hardcoding them.

Pattern: Command. Operations are reified, which is what makes the generation plan in §2.7.9 possible.

Synchronous execution

The default and normative execution model is synchronous. A synchronous operation:

  1. receives a complete request;
  2. validates operation availability against lifecycle state;
  3. validates inputs;
  4. acquires required services;
  5. establishes transaction boundaries if required;
  6. executes;
  7. commits or rolls back;
  8. returns a result or error.

An operation MUST NOT return before its state changes are complete.

This gives deterministic behaviour, simple ownership, predictable Lua integration, easier testing, reliable CLI behaviour, and suitability for lightweight environments such as Termux.

Invocation forms

-- sugar
local result = engine.project.generate(config)

-- explicit, equivalent
local result = engine.execute({
    operation  = "project.generate",
    parameters = config
})

Both MUST map to the same registry entry and produce identical behaviour.

Operation context

Each operation executes within an explicit context containing the engine instance, registered services, the resource index, resolved resources, the filesystem abstraction, transaction state where applicable, and diagnostic facilities.

Operations MUST NOT depend on global mutable state, hidden filesystem paths, environment-specific assumptions, or undeclared external resources.

Rejection

The engine MUST reject operation requests when initialization has not completed, required services are unavailable, shutdown has started, the lifecycle state forbids the operation, or prerequisites are unsatisfied.

Invalid operations MUST fail before performing any partial modification.

Service boundaries

Operations MUST NOT bypass service boundaries. An operation requiring template access MUST use the Template Service; one requiring filesystem modification MUST use the Filesystem and Transaction Services.

The engine MUST NOT expose internal service sequencing as part of the public contract. project.generate may internally perform template expansion, kit application, package installation, asset materialization, and file generation, but callers depend only on the documented operation contract.

Optional job wrapper

The synchronous model MAY be wrapped by a job layer providing progress reporting, cancellation, background execution, and integration with graphical or remote tools.

Job system
    |
    v
Operation
    |
    v
Synchronous engine execution

The wrapper MUST NOT change the operation contract. The same operation MUST behave identically whether executed directly or through a job.

2.4.7 Result handling

All operations MUST return a structured result. Results MUST NOT rely on implicit global state, filesystem inspection, parsing console output, or undocumented side effects.

OperationResult {
    status        success | warning | failure | cancelled
    data          operation-specific payload
    diagnostics   informational messages
    warnings      non-fatal issues
    errors        structured errors
    metadata      affected objects and resources
}

The engine owns creation and lifetime of results. Lua receives a representation across the boundary. The engine MUST ensure returned data remains valid during Lua access and that ownership and memory lifetime rules are explicit. Lua MUST NOT manage internal engine memory.

Results MUST be machine-readable and usable by non-interactive consumers. The presentation format belongs to the consumer; the engine provides information, not user interface policy.

New result fields MAY be added without breaking existing workflows. Existing fields MUST NOT change meaning without a documented compatibility change.

2.4.8 Error handling

Errors are part of the result system. The engine reports failures; Lua decides policy.

The engine MUST NOT terminate the host process because of an operation failure, report errors only as console output, hide failures behind partial success, or allow exceptions to cross the Lua boundary.

Internal C++ exceptions MAY exist but MUST be converted into structured errors before crossing the boundary.

A failed operation MUST leave the engine in a valid state with resources correctly owned, transactions resolved, cleanup possible, and error information available.

Full error taxonomy, categories, codes, and transaction interaction are defined in [[2.15 Error and transaction model]].

2.4.9 Cleanup and shutdown

Shutdown is the controlled transition from an active instance to a released, invalid one. The engine MUST support shutdown after successful execution, failed execution, interrupted workflows, cancellation, and partial initialization failure.

The engine MUST NOT rely on host process termination to release resources.

Order:

  1. Stop accepting new operations.
  2. Complete or cancel active operations.
  3. Commit or roll back pending transactions.
  4. Release temporary operation state.
  5. Release extension services.
  6. Release core services.
  7. Release loaded resources and the resource index.
  8. Release the workspace lock if held.
  9. Destroy the engine instance.

A failed initialization MUST still permit cleanup; the engine MUST track partially initialized state.

Extension shutdown failures MUST be reported but MUST NOT leave the engine undefined, and MUST NOT prevent core cleanup.

Lua MAY request shutdown explicitly. Operations attempted after shutdown MUST be rejected.

A host application MUST be able to create an engine, execute workflows, destroy the engine, and continue running. The engine MUST NOT assume ownership of the host process.

2.4.10 Resource ownership

Host application
    |
    +--> Engine instance
    |        +--> core services
    |        +--> extension services
    |        +--> resource index and loaded payloads
    |        +--> operation state
    |        +--> transaction and staging state
    |
    +--> Lua
             +--> workflow state
             +--> user configuration
             +--> operation decisions

Generated project
    +--> user-owned project files

The engine owns service instances, resource managers, loaded metadata, resolution state, validation state, transaction state, temporary generation resources, and internal caches. It MUST release all of them during shutdown.

Lua owns command-line arguments, user input, workflow state, selected options, script state, and workflow-scoped temporary data. Lua MUST NOT own or manipulate internal engine resources.

Ownership MUST NOT be transferred implicitly, MUST NOT depend on execution order, MUST NOT depend on filesystem location, and MUST NOT depend on process termination. Cleanup MUST occur in reverse dependency order, and a resource MUST NOT be destroyed while an active consumer depends on it.

Generated projects become user-owned at finalization (see [[2.7 Project generation model]] §2.7.12).

The engine MUST always be in exactly one defined state.

Rules:

  • Operations MUST NOT execute before initialization.
  • Initialization MUST NOT occur after shutdown.
  • Shutdown MUST be safe from any valid state.
  • A destroyed instance MUST NOT be reused.
  • Nested operation execution MUST be rejected: an engine in Operating accepts no new operation.

Pattern: State. Transitions are explicit and centrally enforced rather than scattered across service entry points.

2.4.12 Concurrency model

[!note] Resolution of Q-15 (D-015)

  • An engine instance is not thread-safe and has affinity to the thread that created it. All control surface calls MUST occur on that thread.
  • Multiple engine instances MAY coexist in one process, provided no two target the same workspace.
  • Exactly one lua_State per engine instance. Lua state MUST NOT be shared between instances.
  • Exactly one writer per workspace, enforced by an advisory lock (see [[2.15 Error and transaction model]]).
  • The optional job wrapper MAY execute an operation on a worker thread, but only one operation per engine executes at a time, and results MUST be marshalled back to the owning thread before Lua observes them.

Any future relaxation MUST be an explicit, documented compatibility change.

2.4.13 Lifecycle invariants

  • The engine is always in a defined state, and invalid operations are rejected.
  • Initialization is deterministic and free of hidden global state, machine paths, and undocumented external resources.
  • Every engine-owned resource has a defined owner, lifetime, and cleanup responsibility.
  • Boundaries between engine internals, public API, Lua, and generated projects remain explicit.
  • The engine provides capability; Lua provides orchestration.
  • Resource identity is stable and independent of filesystem layout.
  • Operations behave identically regardless of caller.
  • Failure leaves the engine valid, resolvable, and cleanable.
  • Shutdown is deterministic from any valid state.
  • The whole lifecycle works offline from a clean checkout.
