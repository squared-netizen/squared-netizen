2.16 Architectural invariants

[!info] Navigation Index: [[Specification Index]] · Parent: [[2 Generator architecture]] Prev: [[2.15 Error and transaction model]]

Purpose

States the properties that MUST remain true regardless of implementation change, names the section establishing each, and names how each is detected. This is the checklist a reviewer holds a proposed change against.

Outline

Content

2.16.1 The four that outrank the rest

If a change forces a choice, these win:

  1. User work is never destroyed. ([[2.12 Generated-project boundary]])
  2. Generated projects do not depend on the generator. ([[2.12 Generated-project boundary]])
  3. The engine provides capability; Lua provides orchestration. ([[2.1 Architectural model]])
  4. Everything works offline from a clean checkout. ([[1.13 Repository invariant]])

Everything else is a means to these.

2.16.3 On detection

An invariant with no detection mechanism is documentation, not a guarantee. Every row above names one; where the mechanism is weak, that is visible rather than hidden.

This register is the resolution of open question Q-25 ([[Spec open questions]]), recorded as [[Spec decisions#D-028 — Invariant register names a detection mechanism per invariant|D-028]].

I-16's mechanism was strengthened by workspace.verify (§2.16.5), which detects a threatened overwrite before it happens rather than asserting survival afterwards. The half it still lacks is checking a resource in isolation.

I-10 is the weakest and deserves attention: "no undocumented global state" is only partially checkable. The two-instance test catches state that affects results; clang-tidy's check on namespace-scope mutables catches the obvious form. Neither catches state hidden behind a function-local static. This is a known gap.

2.16.4 Changing an invariant

An invariant may be changed, but not quietly. Changing one requires a decision entry in [[Spec decisions]] recording what is given up and why, and an update to every section that relied on it.

2.16.5 workspace.verify

[!note] Resolution of AUD-L-004 (D-052, D-054)

workspace.verify checks a generated workspace against its own provenance record. It is distinct from workspace.inspect, which reports what the record says; verify compares the record against the tree.

It is the first reader of the provenance table. Every generation had written that table — path, ownership class, origin, sha256, one row per file — and nothing had ever read it back. Unread data drifts from correct without failing, so the table was true only by coincidence; verify makes it true on purpose, and its first assertion is that a freshly generated workspace verifies clean.

What it checks, and what each finding means:

ConditionResultBecause
recorded generated file differs from its hashconflicta regeneration would overwrite the edit
recorded generated file absentconflictrecorded but gone; a different remedy, so a different finding
recorded seeded file differscounted, not reportedthat is what seeded means
recorded row carries no hashcounted as uncheckedcopied assets are recorded without one; hiding this would overstate what verify proved

It MUST NOT repair. Restoring a file would be the regeneration path §2.7.11 defers, arriving by a side door. It reports; the remedy is the author's.

It exits non-zero when there are findings, so it composes into a check target or a CI step.

Not yet checked, and named so the gap is visible:

  • Untracked files — present in the tree, absent from the record. Almost always the author's own work, and a useful number. No implementation offers directory listing on its filesystem service.
  • A resource in isolation. Ownership overlaps (§2.7.10) are detected during planning, so a defective template fails when someone generates from it, not before. sqcart performed this check until cartridge format 2.0 removed its jurisdiction (format spec §6), and it has had no successor since. This is the detection mechanism I-16 would want and does not have.
