2.5.1 Architectural role

Lua is the orchestration layer above the native engine. The engine provides capabilities; Lua provides decisions.

Lua is responsible for acquiring user input, loading configuration, selecting workflows, invoking engine APIs, processing results, handling workflow decisions, and controlling generation order.

Lua MUST NOT implement low-level generator capabilities, and MUST NOT replace engine services such as filesystem management, template processing, package resolution, resource management, project generation, or transaction handling.

User / Tool Input
      |
      v
     Lua
      |
      v
Engine Public API
      |
      v
Engine Services
      |
      v
Generated Project

The separation is what allows one implementation to serve command-line generation, custom workflows, embedded tools, IDE integration, automated project creation, and user-defined pipelines.

2.5.2 Lua lifecycle

The Lua lifecycle follows the engine lifecycle:

start Lua runtime
      |
create engine instance
      |
initialize engine
      |
load workflow
      |
execute generation logic
      |
invoke engine operations
      |
process results
      |
shutdown engine
      |
terminate workflow

Lua MUST NOT execute engine operations before the engine reaches Ready. Lua MUST ensure engine shutdown occurs before the host exits.

2.5.3 Workflow orchestration

Lua defines the order and relationship between operations. Workflows MAY select templates, kits, packages, and assets; define generation options; execute conditionally; and implement entirely custom sequences.

The engine MUST NOT determine workflow order.

local cfg = config.load(args)

assert_ok(engine.validate_configuration(cfg))

local tmpl = engine.template.resolve(cfg.template)
local kit  = engine.kit.resolve(cfg.kit)

local result = engine.project.generate(cfg)

The engine executes requested actions. Lua decides why and when.

2.5.4 Command-line interface control

[!note] Resolution of Q-01 (D-025) The earlier draft stated the engine must only receive requests through the Lua boundary, which contradicted the embedded-use guarantees elsewhere. Restated:

The CLI MUST NOT implement generation policy in native code.

The CLI is a thin host: it starts a Lua runtime, creates and initializes an engine, hands control to a workflow, forwards I/O, and reports the final result.

Lua is responsible for parsing command arguments, interpreting switches, loading command configuration, selecting workflows, and formatting user-facing output.

This does not make Lua a mandatory intermediary. An embedding application MAY call the engine C++ API directly (see [[2.1 Architectural model]] §2.1.6). What is prohibited is baking workflow policy into the native layer.

2.5.5 Input handling

Lua provides the input abstraction. Supported sources MAY include command-line arguments, standard input, configuration files, streams, embedded application data, and tool requests.

The engine receives structured data. The engine MUST NOT parse command-line syntax, user prompts, interactive responses, or shell conventions.

2.5.6 Configuration handling

A workflow MAY supply no platforms at all, and SHOULD by default.

An empty platform set means no restriction, not "unknown". Three spellings mean the same thing and all are accepted: the resource declares no platforms, the resource declares all, or the request names none.

A workflow MUST NOT detect the host platform and supply it as a default. The generation host is not necessarily the target — a workspace for Android is routinely generated on a desktop, and on Termux the two happen to coincide, which makes the mistake invisible exactly where it would be made. Detection would also make generation depend on ambient state, which §2.7.2 forbids.

Where a platform genuinely matters, it is the caller's to name.

Lua locates configuration sources, combines values, and selects workflow behaviour. The engine validates configuration data, reports compatibility issues, and processes validated values.

Lua: acquire configuration
        |
Engine: validate_configuration()
        |
Lua: continue workflow

Precedence between configuration sources is a workflow decision and MUST be documented by the workflow, not assumed by the engine.

2.5.7 Engine API interaction

Lua MUST interact with the engine through the public API only.

Lua MAY call services, execute operations, inspect results, handle errors, and control workflow state.

Lua MUST NOT access C++ internal objects, manipulate engine memory, bypass service boundaries, or reach private engine state.

The binding layer MUST preserve ownership rules, lifetime rules, error semantics, and result semantics (see [[2.6 Engine-Lua boundary]]).

2.5.8 Result-driven workflows

Workflows MUST be driven by engine results.

local result = engine.template.resolve(cfg.template)

if result.status == "success" then
    continue_generation(result.data)
elseif result.error.code == "template.not_found" then
    choose_alternative_template()
else
    report(result.error)
end

The engine reports success, failure, warnings, diagnostics, and data. Lua decides whether to continue, retry, amend configuration, or abort.

The engine MUST NOT contain workflow recovery policy.

2.5.9 Filesystem scope

[!note] Resolution of Q-13 (D-013) The earlier prohibition on Lua filesystem access was too broad — Lua must load configuration files and streams. Scoped as follows:

Lua MAY read and write user-space input and output: configuration files, streams, standard I/O, and paths the user explicitly supplied.

Lua MUST NOT:

  • read, scan, or modify generator-owned resources directly;
  • mutate a generated workspace except through engine services;
  • bypass the resource index, manifest validation, or the transaction system;
  • depend on the repository's directory layout.

Any path that will become part of a workspace MUST be written through the Filesystem and Transaction Services, so that provenance and rollback remain correct.

2.5.10 Ownership model

Lua owns workflow state, user interaction, command interpretation, script execution state, and workflow decisions.

The engine owns native resources, services, resource handles, generation state, and transactions.

Ownership MUST NOT cross the boundary implicitly. All cross-boundary resources use explicit APIs.

2.5.11 Invariants

  • Lua controls workflow, not engine internals.
  • Lua selects operations, not implementation details.
  • Lua owns decisions, not native resources.
  • Engine results drive workflow decisions.
  • CLI behaviour is separate from engine capability.
  • Workflows remain programmable after release (see [[2.14 Extensibility model]]).
  • Lua execution is deterministic given identical inputs.
  • The engine remains usable without any particular Lua workflow.
