2.13.2 Per-component rules

third_party/ — a leaf. Depends on nothing in the repository. May be depended on by engine/ only. lua/ MUST NOT depend on vendored C sources directly; it reaches Lua libraries through the runtime the engine embeds. Third-party code MUST NOT define Squared project architecture.

engine/ — depends on third_party/ and on the C++ standard library. Depends on resources/ only as data, reached through the Resource Service by identity. MUST NOT depend on lua/ workflow code; it exposes a binding surface, it does not consume workflows. MUST NOT depend on generated projects.

lua/ — depends on the engine public API through the binding layer. MUST NOT depend on engine internals, on third_party/ sources, on resources/ layout, or on generated projects. Reaches resources by identity only.

resources/ — inert data with no outgoing dependencies. Resources declare dependencies on other resources in their manifests, which the engine resolves; those declarations are data, not code coupling. A resource MUST NOT reference engine/ or lua/ implementation.

hosts (the CLI, embedding applications, tools) — depend on engine/, and on lua/ when they host workflows. Nothing in the repository depends on a host.

Generated projects — sinks. Depend on the Squared framework and on their own declared external dependencies. Nothing in squared-pg may depend on a generated project ([[2.12 Generated-project boundary]]).

Squared framework — external to this repository. Consumed by generated projects. The framework MUST NOT depend on squared-pg.

2.13.3 Resource dependency sub-graph

Resources depend on each other through manifest declarations, resolved by the engine:

template  --requires-->  kit
template  --requires-->  package
kit       --requires-->  package
package   --requires-->  package
package   --requires-->  asset
kit       --requires-->  asset

Prohibited edges in this sub-graph:

  • package -> template — a package MUST NOT require a specific template as a dependency; it MAY declare template compatibility, which is a constraint, not an edge.
  • asset -> anything — assets are leaves. An asset MAY declare package requirements as compatibility constraints, not as dependencies it pulls in.
  • Any cycle. The resource dependency graph MUST be acyclic, and cycles MUST be reported with the full path.

The distinction between a dependency (pulls the target into the resolved set) and a compatibility constraint (restricts what the resolved set may contain) is load-bearing and MUST be preserved in manifests.

2.13.5 Acyclicity

The graph MUST be acyclic. A deliberate cycle requires an explicit decision entry in [[Spec decisions]] naming the cycle, the justification, and the mechanism that prevents it from becoming load-bearing. No such cycle currently exists.

2.13.6 Enforcement

A dependency rule that is not tested decays. The following SHOULD be enforced automatically:

RuleMechanism
engine/ does not include lua/ workflow codeinclude-path check in CI
lua/ does not reach engine internalsbinding surface is the only registered API; audit registered symbols
resources/ contains no executable codefile-type check over resource roots
Resource graph is acyclicresolver rejects cycles at initialization; test with a deliberate cycle fixture
No absolute host paths in generated outputgrep check in the generated-project conformance suite
Component build isolationengine/ builds and its tests pass with lua/ absent

The last check is the strongest single guarantee: if the engine builds and tests green without the Lua layer present, the capability/orchestration split is real rather than aspirational.
