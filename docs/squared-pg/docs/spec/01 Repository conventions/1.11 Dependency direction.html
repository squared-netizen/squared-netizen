1.11 Dependency direction

[!info] Navigation Index: [[Specification Index]] · Parent: [[1 Repository conventions]] Prev: [[1.10 Naming]] · Next: [[1.12 Development instructions]]

Purpose

States the repository-level dependency constraints. The authoritative graph is [[2.13 Dependency graph]] (D-026).

Outline

  • ☑ requirement for explicit, reviewable boundaries
  • ☑ constraints holding regardless of component detail
  • ☑ authoritative graph reference

Content

The repository MUST maintain explicit and reviewable dependency boundaries.

The following constraints apply at the repository level:

  • Generated applications MUST NOT become dependencies of the generator.
  • third_party/ dependencies MUST remain implementation dependencies of the repository and MUST NOT define Squared project architecture.
  • Dependencies between engine/, lua/, resources/, and generated projects MUST be explicit rather than relying on undocumented global state, implicit filesystem coupling, or machine-specific paths.
  • A component MUST NOT depend on another component merely because its implementation happens to reside in the same repository.
  • Public interfaces crossing component boundaries MUST be documented and testable.
  • The dependency graph MUST be acyclic unless a deliberate cycle is explicitly justified and documented.

The authoritative dependency graph and the permitted relationships between components are defined in [[2.13 Dependency graph]]. In summary:

third_party/  <--  engine/  <--  lua/  <--  hosts (CLI, embedders)
                      |
                      | reads (identity only)
                      v
                 resources/          -> Generated Project (sink)

resources/ is inert data with no outgoing dependencies. Generated projects are sinks: nothing in the repository may depend on them.
