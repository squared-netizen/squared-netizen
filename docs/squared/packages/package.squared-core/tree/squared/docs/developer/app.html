app &mdash; internals

The platform-neutral boundary: twelve types, no translation units, no dependencies beyond sq::graphics::Context (forward declared). Since 7.1 its Application is implemented by sq::App (stage.md), not by an app.

Programmer counterpart: ../programmer/app.md

  • Public types: 12
  • Translation units: 0 &mdash; every type is a value type or a pure interface

Layout

app/
  application.cppm event.cppm runtime.cppm safe_area.cppm
  src/   the eleven supporting headers: key, modifiers, navigation, text input,
         the clipboard service (12.4), the background service (12.6), and report

Since 7b.4 app is a built module, sq.app, with a Makefile and libsquared_app.a: its interfaces have objects (the module's initializer, and member functions defined in a class, which are not implicitly inline in a module). It has no implementation units. runtime.cppm imports sq.graphics, sq.files and sq.assets for the references Runtime holds (a module cannot declare another's types ahead), so app is built after them. See file-layout.md and modules.md.

The one deliberate rule deviation

application.cppm names Event and TextInputService only by reference, so the tree's forward-declare-or-include rule would make both forward declarations. It includes them instead, because application.cppm is also this module's aggregate header: Application cannot be implemented without both, and there is no free name left for a separate <module>/<module>.hpp umbrella with the class already holding it.

event.cppm is likewise the Event struct rather than a group umbrella. It includes key.cppm, key_modifiers.cppm and navigation.cppm, because Event holds all three by value.

The report sink and the lifecycle calls (7.1)

Report is a function pointer and a void * context, 16 bytes, with an operator() that does nothing when empty: the platform gives one (set_report, before create()), and the App and the Stage say each failure through it, one line, with no allocation and no logging library of their own (the framework above the porting layer names no Android header). Chosen over std::function (heap and type erasure, standard-library-deviations.md) and over a virtual sink interface (a vtable for one call).

foreground(), background() and low_memory() are Android's start, stop and low-memory commands, which the glue already delivers: three virtual calls with empty defaults, so an Application written before them (the demo's) compiles and behaves as it did. They are events: nothing polls.

What Android keeps, back to the background, the bars (7.8)

Four more defaulted virtuals, so the demo's Application compiles as it did:

  • set_saved_state( std::span<const std::byte> ), before each create(): Android's saved instance state for the activity, empty for a new launch. A view, valid until create() returns: the platform owns the bytes (the template takes the glue's savedState at android_main's start, because the glue frees it at the first resume, before there is a window, and frees it after the first create()).
  • save_state( std::span<std::byte> ), on APP_CMD_SAVE_STATE: at most saved_state_bytes (8,192), written into the platform's buffer (on the glue thread's stack), which copies what was written with malloc into the glue's savedState; the glue hands it to Android and frees it.
  • take_background_request(), each loop turn: a one-shot flag. A flag read by the platform rather than a call into it: the App holds no platform pointer, and the platform already reads quit_requested() the same way.
  • hides_bars(), each frame: a bool read and compared with the last answer; a change, or a focus gained, is the only time the platform acts. A bool per frame over an event because the answer is the Stage's (hide_bars), set by app code at any time, and the comparison is cheaper than a notification path.

Why Android's saved state and not a file (the user's pick, 2026-10-27, "Saved state"): Android keeps it exactly when the app should come back where it was (it ended the process itself) and drops it exactly when it should not (a swipe from the recent apps, a finish, a force stop, a reboot). A file cannot tell those apart without getHistoricalProcessExitReasons (API 30, so not the tablet). Priority 1 as well: no file, no fsync, the bytes held by Android's process, not this one.

Memory

Event carries a std::string text member for TextInput and TextEditing events, which makes it 80 bytes (libc++, measured; 88 under libstdc++) and heap-capable, and it is passed by const reference everywhere &mdash; so no copy is made on the dispatch path. The platform adapter owns the one live Event. KeyModifiers is one byte (static_asserted). TextInputArea is four floats.

Nothing in this module allocates on its own behalf.

ClipboardService (12.4) is an interface like TextInputService: a virtual pair the platform implements, one pointer handed to the App. A virtual here is off the frame path (a copy or a paste, on a tap). Chosen over a function pointer and a context (two, one each way, for a pair of calls a person makes by hand) and over the Stage calling JNI (platform code above the porting layer). text reports the whole size so a caller sizes once and allocates once; on Android the clip is read 512 UTF-16 units at a time on the stack (AndroidText::clip_read), so the platform allocates nothing but what JNI does.

BackgroundService (12.6) is the same shape, with one difference in its lifetime: the platform's object is the process's, not an activity's (a foreground service outlives the activity that started it), so it is given before create() and never taken back. Its title and text are copied into two 64-byte arrays on the platform's side; nothing is allocated on the application's.

One vocabulary for keys

Before Sprint 3.1b there were three key enums, two modifier types and two navigation enums for the same things:

  • keys: app::Event::Key, gui::Key (without unknown, so offset by one) and gui::InputKey;
  • modifiers: app::KeyModifiers (a one-byte bitset driven by an app::KeyModifier flag enum) and gui::InputModifiers (four bools), with gui::KeyModifiers an alias of the second;
  • navigation: app::Event::Navigation and gui::NavigationAction.

gui::Ui and gui::Widget carried six switch statements converting between them.

Now there is one of each, in this module, because it is the lowest layer that both the platform entry file and the GUI see: app::Key, app::KeyModifiers and app::Navigation. The GUI routes them unchanged, and the conversions are gone (243 lines out of ui.cpp and widget.cpp). Pinned by gui/test/ui_keys_test.cpp: every named key arrives as itself, with its modifiers, and focus moves as it did.

KeyModifiers is four one-bit bool fields with default member initializers.

  • Priority 1: it stays one byte, where gui::InputModifiers was four, which takes gui::InputEvent from 88 to 80 bytes.
  • Priority 2: callers read fields (modifiers.shift) and build with designated initializers (KeyModifiers{ .shift = true }), instead of contains(), set() and operator|.

== is defaulted, and any() replaces empty().

Safe area

SafeArea is four std::int16_t (8 bytes, static_asserted), passed by const reference. Application::safe_area_changed() is a defaulted virtual, so an application that ignores it costs nothing and an old one still compiles.

Measuring (Android). NativeActivity has no call for the bar sizes, so the platform entry file asks the Java side through JNI: Activity.getWindow() &rarr; getDecorView() &rarr; getRootWindowInsets(), then getSystemWindowInsetLeft/Top/Right/Bottom() and, where there is one, the DisplayCutout's safe insets, combined with max. Those getSystemWindowInset* methods are deprecated from API 30 but present on every release squared targets, and they avoid a second code path keyed on the SDK level. Every step tolerates failure and falls back to zero, so a release where a call is missing behaves as before.

The query runs on events only (7.8, the user's pick "Measure on events"): for 12 frames after a drawable-size change or a new window, for 24 after the bars are hidden or shown and after the keyboard is shown or hidden (they slide), and every 30th frame while the keyboard is up, because the user can close it with the back gesture and the app hears nothing. With the keyboard down and the bars hidden it never runs. Until 7.8 it ran every 30th frame always: 64 JNI calls, 12 of them into Java, twice a second at 60 Hz. The bounded runs are deliberate: the insets are not available when the first window arrives and APP_CMD_CONTENT_RECT_CHANGED does not reliably report an edge-to-edge window, so the answer is asked for until it settles. Cost per query: about ten JNI calls, no allocation on the native side (every local reference is deleted), and the thread is attached to the VM once and detached at shutdown. The call is made from the native thread rather than the UI thread; these are plain getters on state the framework already published, which is how other native frameworks read them.

The UI thread (7.8). Hiding the bars touches the window's views, which belong to Android's main thread, while the glue runs everything else on its own. The manifest names squared_on_create (android.app.func_name, read by NativeActivity) as the entry: on the main thread it makes a pipe (pipe2, non-blocking, close-on-exec), adds its read end to that thread's ALooper with a callback, records it against the activity (two slots: the next activity can be made before the last is destroyed), calls the glue's ANativeActivity_onCreate, and wraps the glue's onDestroy so the pipe is closed after the glue's thread has ended. The glue's thread posts one-byte jobs (hide_bars, show_bars, to_back); the callback runs them with the activity's own JNIEnv. A pattern: a command queue over a pipe, the looper's own wake-up, chosen over a Java shim (no Java, decided 2026-10-15) and over calling from the glue's thread (Android may refuse a view call from another thread). Cost: two file descriptors and 48 bytes of slots per process, one write per job. Without the manifest line the glue starts as before: the bars stay, and to_back is called from the glue's thread (moveTaskToBack is a binder call, safe from any thread).

The bars: WindowInsetsController.hide( WindowInsets.Type.systemBars() ) with BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE from API 30; View.setSystemUiVisibility( IMMERSIVE_STICKY | FULLSCREEN | HIDE_NAVIGATION | the three LAYOUT flags ) from 19 to 29. Asked again after each focus (a dialog or the keyboard can bring them back on the older releases).

Known limitation: the JNI code lives in the seeded sq_android/entry.cpp, so each generated project carries a copy. When the app module gets a compiled library, it belongs there.

Runtime

A non-owning bundle of three references: graphics::Context, files::FileSystem, assets::AssetManager. Twenty-four bytes. The platform layer owns the objects; Runtime only points at them.

Admission rule. A service belongs in Runtime only if its lifetime is the whole process and only the platform layer can construct it. The context needs the native window; the file system needs AAssetManager and the app's storage paths; the asset manager needs the file system. All three pass. A sprite batch, a skin or a UI fails the second test &mdash; the application can build its own &mdash; and stays out.

That rule is the whole defence against this becoming a Service Locator. It is not global, nothing reaches in by type, and it is passed once, explicitly, to create(). The rule is what stops it growing into the object every subsystem reaches into.

Why references, not ownership. FileSystem is polymorphic &mdash; PosixFileSystem in Termux, AndroidAssetFileSystem on device. Owning it would mean a unique_ptr and a heap allocation, or a template parameter on the platform type. Referencing needs neither: the platform holds the concrete type by value.

Why only create(). render() keeps taking the context alone. Passing the whole bundle every frame invites reaching for the file system or the asset cache at sixty hertz.

Construction order. In entry.cpp's Platform, member order is construction order: context, file system, asset manager, runtime, then the application. The asset manager refers to the file system and the runtime to all three, so each is declared after what it refers to, and the application comes last so everything it is handed already exists.

The header forward declares all three and includes none, so it adds nothing to a translation unit that only needs the type. An App that calls into a member includes that member's header itself.

SQUARED_PLATFORM must be passed, not just set

pkg_squared_core.mk chooses the platform and must pass it through the squared-core recipe. For a while it was set to android and never passed: the framework fell back to its default, posix, and every APK shipped a files library without AndroidAssetFileSystem in it. Nothing failed at build time.

A selector that is set but not passed is silently ignored. Every one has to appear in the recipe.
