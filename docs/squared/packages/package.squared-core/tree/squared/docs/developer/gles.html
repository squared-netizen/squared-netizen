gles &mdash; internals

Public GL object layer over GLES 3.0.

Programmer counterpart: ../programmer/gles.md

  • Public types: 16
  • Translation units: 6

Why it is public

It is the layer someone reaches for when they want a custom shader alongside the widget set, and it is the layer OpenGL teaching tooling is built on. libGDX exposes its equivalent (glutils) for the same reasons.

Being public costs an API surface that has to stay stable. That is paid for deliberately, and it is why the types name things in squared's own enums rather than raw GLenum &mdash; BufferTarget::Index survives a backend change in a way GL_ELEMENT_ARRAY_BUFFER does not.

No CPU-side mirror of anything. That is the priority-1 decision at the centre of the module. Retaining pixel data would make recovery after context loss automatic and would double the resident cost of every texture in the application. Recovery policy lives in graphics::Texture, where the caller chooses per resource; this layer only offers what a policy needs.

invalidate() is the non-obvious one

Every object has both destroy() and invalidate(), and calling the wrong one after context loss produces corruption that reads as a driver bug.

destroy() calls glDelete*. After the context is gone, the name belonged to a context that no longer exists: at best the call is a no-op, at worst the same integer now names a different object in the new context and gets freed under its owner.

invalidate() zeroes the name and touches no GL.

This is why the pair exists rather than a single reset(): the two cases look identical at the call site and behave nothing alike, so they have different names.

Introspection is a query, not a cache

Program::attributes() and Program::uniforms() fill a caller-owned vector and store nothing. A program drawn with sixty times a second is introspected once, by a person or a tool, so the lists cost nothing until somebody asks. Same pattern as files::FileHandle::list() and for the same reason.

glGetActiveAttrib reports an index, not a location, so each entry is followed by a glGetAttribLocation call. They differ, and conflating them is a common bug.

Two driver traps handled here

GL_UNPACK_ALIGNMENT is set to 1 before every upload. GL unpacks rows on a four-byte boundary by default, so an R8 texture whose width is not a multiple of four is read with a gap at the end of every row. The symptom is a font atlas that comes out sheared, and it only appears at certain widths.

A new texture gets sampling defaults immediately. GL's default minification filter is mipmap-based, so a texture with no mipmaps samples as black. Setting Linear/Linear/ClampToEdge at creation means a freshly created texture draws.

Standard library deviations

None worth recording. No std::function, no std::shared_ptr, no std::unordered_map. std::string appears only in GlesError::message and in the introspection structs, both of which are diagnostic paths rather than per frame. std::vector is used for driver log buffers, whose length only the driver knows.

Build wiring

The module is in MODULES only when SQUARED_GRAPHICS_BACKEND is gles, because it cannot compile without the NDK's GL headers. The root Makefile reads local.mk directly for that test: module Makefiles reach local.mk through build/common.mk, but the root one does not include common.mk, so a backend chosen in local.mk would otherwise select the right context.cpp and the wrong module list.

Shared vocabulary with graphics

Texture2D::set_sampling() takes graphics::TextureFilter and graphics::TextureWrap. Until Sprint 3.1b this module had its own copies of both enums, with the same values. gles already depends on graphics in the root Makefile (gles: graphics), and graphics is always built while gles is not, so the shared pair lives in graphics. Only the two headers are shared, and nothing is linked. The two small to_gl_filter/to_gl_wrap helpers are still written twice, here and in graphics/src/gles/texture.cpp, because the graphics backend must not depend on this module.

Testing against a fake driver

make -C gles test links the module against test/gl_stub.cpp, which defines the GL entry points this module calls. The stub is compiled against the real GL headers, so every signature is checked by the compiler rather than by hand, and it records what was called.

That records-what-was-called property is the point. It lets the test assert things no real driver can be asked about, and the one that matters most is:

texture.invalidate();
assert(!glstub::deleted("glDeleteTextures", name));

On a device, getting that wrong frees an unrelated object in the new context and the corruption reads as a driver bug. Here it is one assertion.

The suite also covers: destroy() deleting exactly once even when called twice, move construction not double-deleting, compile and link failures carrying the driver's log, shaders being detached after linking, introspection reusing the caller's vector, GL_UNPACK_ALIGNMENT reaching 1 before an R8 upload, sampling defaults being set at creation, out-of-range regions and short pixel spans being refused before they reach GL, and a -1 attribute location being skipped rather than passed through.

What it does not prove: that a real driver accepts these enum combinations, that GL_R8 exists on the target, or that anything renders. Those need a device.

Not yet written

Framebuffer for render targets, and uniform buffer objects beyond BufferTarget::Uniform existing as an enumerator. Neither has a second concrete use yet; see extension-policy.md.
