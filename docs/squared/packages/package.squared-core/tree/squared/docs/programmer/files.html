files

Virtual filesystem. A FileHandle names a location; a FileSystem decides what that location actually is on this platform. Modelled on libGDX.

The shortest call site

sq::files::PosixFileSystem fs{ {
    .internal_root = app_directory + "/assets",
    .local_root    = app_directory + "/files",
    .external_root = "/sdcard/MyApp"
} };

auto skin = fs.internal("skins/default.json");
if (auto text = skin.read_string()) {
    load_skin(text.text);
}

File types

The same relative path means a different file under each root, and the platform decides what each root is:

TypeAndroidTermux and desktop
Internalassets inside the APK, read-onlya directory, still read-only
Localthe app's private files directorya directory
Externalshared storagea directory
Absolutethe path exactly as giventhe same

Internal refuses writes on every platform, even where it is an ordinary writable directory. A build that works in Termux therefore behaves the same on a device, instead of failing the first time someone runs the APK.

Handles are values

A handle is 48 bytes: a file system pointer, a type, and a path string. Constructing one touches nothing, so building handles in a loop costs only the strings. Nothing is opened until an operation is called and nothing stays open after one returns.

auto atlas = skin.sibling("default.atlas");   // skins/default.atlas
auto dir   = skin.parent();                   // skins
auto page  = dir.child("pages/0.png");        // skins/pages/0.png
skin.name();                                  // default.json
skin.extension();                             // json
skin.name_without_extension();                // default

Failures are returned

Nothing throws, and a missing file is an ordinary result rather than a programmer error:

auto bytes = handle.read_bytes();
if (!bytes) {
    log(bytes.error.code, bytes.error.message, bytes.error.path);
    return;
}
use(bytes.bytes);

What each operation returns when it fails, on PosixFileSystem:

OperationFails with
any, on a path with .. or a leading /, or a type with no rootNotSupported
write, make_directories, remove on InternalReadOnly
read of a missing fileNotFound
read of a directoryIsADirectory
write into a missing directoryNotFound (write_bytes on a handle makes the directories first)
write onto a directoryIsADirectory
list of a missing path, or of a fileNotFound, NotADirectory
make_directories where a file is in the way, or is the pathNotADirectory
remove of a missing path, or of a directory that is not emptyNotFound, IoFailure

exists(), is_directory() and length() return plain values, because there is no useful difference between "missing" and "could not tell". length() returns zero for a missing file, a directory, and an empty file alike; use exists() when the difference matters.

Reading in place: map (12.3d)

A file read now and then for as long as the app runs (a font FreeType reads a glyph at a time, a table looked up by offset) is mapped rather than read: no copy on the heap.

sq::files::MapResult font = fs.internal("fonts/JetBrainsMonoNL-Regular.ttf").map();
if (!font) { report(font.error); return; }
face.open(font.file.bytes());     // valid while `font.file` lives
CallDoes
handle.map(), fs.map( type, path )a MapResult: the MappedFile, or the error (NotFound, IsADirectory, NotSupported for a path that escapes its root, a root that is not set, or a non-Internal embedded file)
file.bytes()the file's bytes, read in place; empty for an empty file
file.valid()a file is mapped (an empty one is)
file.in_place()the file's own pages (mmap, an asset stored uncompressed, an embedded file), not a copy
file.reset(), the destructorgive it back; bytes() is empty after

MappedFile is move-only (40 bytes). Its pages are clean: Android can drop them under memory pressure and read them again, and only what is touched is resident. An asset is mapped in place only when the APK stores it uncompressed: the template's packaging stores ttf, otf and ttc so (SQ_STORED in the project's Makefile adds more). A compressed asset still maps, into memory Android unpacks it to, and in_place() is false: check it once in a dev build.

Writing

auto save = fs.local("saves/slot1.json");
if (auto error = save.write_string(document)) { report(error); }

Missing parent directories are created first, as libGDX does, so writing to a fresh path needs no setup call.

A save that must not be half written (the process can die during it):

if (auto error = fs.local("saves/slot1.json").write_atomically(document)) { report(error); }

write_atomically( bytes ) and write_atomically( text ) write beside the file (slot1.json.new), flush it to storage, and rename it over the file: whoever reads it gets the old contents or the new, whole. Missing parent directories are created first. Failures as write's, and on any failure the file is as it was and nothing is left beside it. Internal refuses it (ReadOnly), as it refuses every write. The same on Termux, a desktop and a device: private storage is a directory on each.

The platform's own path, for code that outlives the file system it came from (a thread that saves after the activity has gone):

const std::string path = fs.resolve_platform_path(sq::files::FileType::Local, "saves/slot1.json");

Empty when there is none: bundled files inside an APK, compiled-in files, a root that is not set, a path that escapes its root. Use it later with FileType::Absolute through any file system.

Listing

std::vector<sq::files::FileHandle> entries;
if (!fs.local("saves").list(entries)) {
    for (const auto& entry : entries) { ... }
}

The caller owns the vector so it can be reused across calls rather than allocating a new one each time, which is why this does not return a value.

Paths that escape their root

A relative path containing .., or starting with /, is refused rather than normalised, with FileErrorCode::NotSupported. Asking for something under a root and quietly getting something outside it would be worse than failing. Use FileType::Absolute when you mean an absolute path.

Files compiled in: EmbeddedFileSystem

Small files the program cannot do without (the Stage's default skin is one) can be compiled into it and read like bundled files, with nothing to package. tools/embed_files.sh turns a directory into a C++ source: the files' bytes as constants, and a table of EmbeddedFiles that a function returns:

tools/embed_files.sh sq_app/data data my_data detail/my_data.hpp sq_app/src/my_data.cpp

(the directory, the path its files appear under, the function's name in sq::detail, the header that declares it, the output). Then:

sq::files::EmbeddedFileSystem files( sq::detail::my_data() );
const auto text = files.internal( "data/levels.json" ).read_string();
CallAnswers
exists, is_directory, lengthfrom the table: a directory is any path some file is under; only Internal holds anything
reada copy of the bytes; NotFound, IsADirectory; NotSupported outside Internal
listthe names directly under a path, each once, sorted; NotADirectory, NotFound
write, make_directories, removeReadOnly

The table must outlive the file system: a generated one is a constant. The bytes are read-only data in the program, mapped from its file and shared, not heap; a read copies them. Lookups scan the table, so keep it to a handful of files.

Nested assets on Android

Organise assets in as many directories as you like &mdash; reads work at any depth, on every platform:

fs.internal("audio/sfx/ui/click.ogg").read_bytes();
fs.internal("skins").list(entries);          // returns default/ on device too

On Android, listing and is_directory() are answered from an index the build writes into the APK at assets/SQ-INF/index. You do not create or maintain it; make apk regenerates it whenever an asset changes, and an app update replaces it along with everything else, so it cannot go stale.

Two things to know:

  • Keep sq_android/assets/SQ-INF/index in your .gitignore. It is a build product.
  • Do not put assets under assets/SQ-INF/. It is the bundle's metadata directory, excluded from the index and hidden from listings &mdash; from Internal's root listing in Termux and on a desktop too, so every platform lists the same names.

The details, and why it works this way rather than any of the obvious alternatives, are in ../developer/asset-index.md.
