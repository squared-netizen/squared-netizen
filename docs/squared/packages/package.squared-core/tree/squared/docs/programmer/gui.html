gui

The libGDX-flavoured widget set and skinning, on top of the scene graph they're built from: Actor, Group, Widget and input routing. sq::Stage holds the widgets of an app's screens and panes (stage.md); the host types under it are internal since 7.7 (Panes and the host).

import sq.gui; gives every type here, and the sq::graphics and sq::app types the widgets' interfaces name. Each type is written in a file of its own, a partition of the module: the ones at the module root (squared/gui/*.cppm) are the everyday ones, those under squared/gui/src/ the supporting types they are made of. See include-layout.md.

Developer counterpart: ../developer/gui.md

Screens and panes as data &mdash; the node table, writing one from C++, layout files and names.json compiled by sqgen, and building widgets from it &mdash; are on their own page: layouts.md.

What you subclass is Widget: a custom node (app.stage.custom( "minimap", make )) is one. Actor (position, size, parent, input listeners) and Group (children) are its bases, kept apart because a widget's children are actors of any kind; an app does not make an Actor or a Group of its own (decided in 7.7).

A widget of your own takes keys by overriding key_down, with the sq::app types:

bool key_down(sq::app::Key key, sq::app::KeyModifiers held) override
{
    if (key != sq::app::Key::enter || held.any()) return false;
    activate();
    return true;
}

What a key types with Ctrl, Alt or Meta held goes to key_text, not text_input (12.3d): Ctrl-C arrives as key_text( "c", {.control = true} ). A text field leaves it (the default returns false), as a desktop's does; a terminal turns it into a control character (sq::term::key_text_bytes). Shift alone is typing, and goes to text_input.

bool key_text(std::string_view text, sq::app::KeyModifiers held) override
{
    if (!held.control || text != "s") return false;
    save();
    return true;
}

Pinch

A two-finger pinch zooms the whole UI in every squared app (stage.md). A widget that has a better use for it (a terminal's font, a map's view, an image) takes it by overriding pinch. As the second finger lands, the widget under the fingers' middle is offered begin, then its parents, until one returns true; that one gets the changes and the end, and the UI does not zoom. scale is the fingers' distance over what it was as they started to move (1 at begin, 2 with them twice as far apart; end carries the last). The first finger's press was cancelled before begin (PointerAction::cancel), and neither finger reaches pointer_event until both are up. The return value after begin is ignored.

bool pinch(const sq::gui::PinchEvent& event) override
{
    if (event.phase == sq::gui::PinchPhase::begin) start_ = zoom_;
    else zoom_ = std::clamp(start_ * event.scale, 0.5F, 4.0F);
    return true;  // mine: the UI stays as it is
}

A widget that leaves it (the default, false) changes nothing: the UI zooms over it as over anything else.

List is what a layout's list node builds; the Stage binds it to a model's list (stage.md), and an app rarely touches it. Its rows are one node of a layout, copied, and built as a Table for each row on screen and one more; all are one height, the first row's. set_count(n) says how many rows there are; set_on_row(shown, context) is told each time a row's table starts showing another row (row_at(slot), slot_showing(row)); set_scroll_y(offset) scrolls it, and a drag does, anywhere in it: once a finger has moved drag_slop (8 units) on a row's button, the button lets go and the list scrolls. first_row() and rows_on_screen() say what shows. At most max_rows_built (64) row tables; a list that would need more leaves the rest empty (short_of_rows()). Button::pressed() is public now, so a button a list took the finger from can be seen to have let go. restore_scroll(offset) scrolls to offset once the rows reach it: as far as they go until then (the count may not have come yet), and forgotten by any scroll since. What the Stage puts back when a screen comes back.

A Table lays out without allocating, once each depth of tables has been laid out at its largest: its working sizes are kept between layouts. Table::release_kept() frees them (on low memory; the next layout makes them again), and Table::kept_count() says how many sets there are, one a depth.

ScrollPane, TextField and List answer actor_cast (below) by their own type.

When an edit is finished. TextField::set_on_commit( callback, context ) calls callback( context, field ) on Enter (the keyboard's Done), and when the field loses the focus after its text changed; field.text() is the edit. A function pointer and a context, so it allocates nothing; nullptr for none. focused() says whether the field has the focus now, and edited() whether its text changed since the last commit: an edit not finished. restore_edit( text ) puts one back, as set_text with edited() true: committed, as any edit, on Enter or on leaving the field.

void named( void *context, sq::gui::TextField &field ) { /* field.text() */ }

field.set_on_commit( &named, &player );

Label::set_text and TextField::set_text take a std::string_view and copy it into the widget's own text, which keeps its storage: setting a text no longer than one the widget held allocates nothing.

Slider::dragging() is true while a pointer holds the knob: what the Stage uses to keep a model's value off a slider being moved (stage.md).

Panes and the host

An app's panes are the Stage's (stage.md): a layout of kind pane, or a C++ screen opened as one. Since 7.7 the types under them are internal, in squared/gui/src/detail/ (not part of the API, and not listed with the rest):

WasNow
gui::Ui, squared/gui/ui.hpp: the host of one widget treeinternal (src/detail/ui.cppm); the Stage holds one per window
gui::Stage, squared/gui/stage.hpp: the tree's rootinternal, gui::ActorRoot (src/detail/actor_root.cppm): one Stage, the app's
gui::Window, squared/gui/window.hppgone: a pane's frame is gui::PaneFrame (internal), the skin's pane window style around a table, with no title bar, dragging or resizing
gui::Dialog, squared/gui/dialog.hpp, Ui::show_dialoggone: a question is a pane layout with buttons ("tap": "close", "tap": "quit", a telegram)

The demo, which runs its own screens on the Ui until it moves to sq::App (Sprint 9), includes the internal header by its path.

The safe area. The Stage keeps its screens and panes inside the part of the screen the user can see, from what the platform says (Application::safe_area_changed()): nothing for an app to do.

Navigation waits for the tap. A tap's push, back or open is applied after the tap has been delivered, since building the next screen frees the tapped button (stage.md).

Skin loading

load_libgdx_skin reads a libGDX uiskin.json. Style tables may be keyed by the full libGDX class name (as a stock skin has them) or by its last part: com.badlogic.gdx.scenes.scene2d.ui.TextButton$TextButtonStyle and TextButton$TextButtonStyle are the same table. Supported: Color, BitmapFont, Skin$TintedDrawable, Button$ButtonStyle, TextButton$TextButtonStyle, TextField$TextFieldStyle, Label$LabelStyle, CheckBox$CheckBoxStyle, Slider$SliderStyle, ProgressBar$ProgressBarStyle and Window$WindowStyle; any other class in the file is reported as a warning. Giving one class twice, once in each form, is an error.

Lua: not bound.

Text-entry widgets and the soft keyboard

The Stage raises, moves and stops the platform text-input service based on Widget::wants_text_input(). It returns false by default and TextField returns true, so a custom text-entry widget opts in by overriding it:

class CodeEditor final : public sq::gui::Widget {
public:
    [[nodiscard]] bool focusable() const noexcept override { return true; }
    [[nodiscard]] bool wants_text_input() const noexcept override
    {
        return true;
    }
};

Without the override the widget still takes keyboard focus and still receives text_input(), but the on-screen keyboard is not raised for it on Android.

Downcasting an Actor

squared builds with -fno-rtti, so dynamic_cast is not available. Use actor_cast instead:

for (std::size_t i = 0; i < group.child_count(); ++i) {
    if (auto* widget = sq::gui::actor_cast<sq::gui::Widget>(
            group.child_at(i))) {
        // this child is a Widget
    }
}

It accepts null, returns null when the actor does not publish the requested interface, and has a const overload. Group and Widget both work as the target type.

To make your own Actor subclass reachable the same way, publish an identifier and override both actor_interface overloads, delegating to your direct base for identifiers you do not recognise:

class MyNode : public sq::gui::Group {
public:
    static constexpr sq::gui::ActorInterfaceId
        actor_interface_id = 0x4D'59'4E'44U;

    [[nodiscard]] void* actor_interface(
        sq::gui::ActorInterfaceId id) noexcept override
    {
        return id == actor_interface_id ? this : Group::actor_interface(id);
    }

    [[nodiscard]] const void* actor_interface(
        sq::gui::ActorInterfaceId id) const noexcept override
    {
        return id == actor_interface_id ? this : Group::actor_interface(id);
    }
};

Drawing the interface

Widgets draw through a Painter. BatchPainter is the one that puts them on screen:

import sq.gui;

// Once, after the skin's atlas and font are loaded:
sq::gui::BatchPainter painter{batch, font.get()};   // font: the skin's FontPtr
const sq::graphics::AtlasRegion* white = atlas.find_region("white");
if (!painter.set_fill_source(white != nullptr ? &white->region() : nullptr)) {
    // no fill source at all; solid fills are skipped
}
painter.set_viewport(640.0F, 480.0F, graphics.pixel_width(),
                     graphics.pixel_height());

// Every frame, between batch.begin(camera) and batch.end(): your own drawing
// (the Stage lays out and paints its widgets through the same calls).
painter.draw_text("score", 16.0F, 16.0F, font.get(), sq::graphics::Color::white());

Keep one painter for the life of the interface. It holds the scratch storage text is laid out in, so a new painter per frame would allocate again.

Call set_viewport() again on resize. Only clipping needs it.

Pass the skin's white region. Solid fills are drawn from it, so they share an atlas page with every other widget graphic and the interface costs one draw call instead of one per fill. Both stock skins ship a white region for exactly this. Passing nullptr works and costs a draw call per fill.

Clipping is handled for you: a scroll pane pushes a clip, and anything drawn inside it is scissored to that rectangle. Nested clips intersect.
