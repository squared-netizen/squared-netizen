stage: the App and the Stage

Internals: ../developer/stage.md.

An app is a model and its screens. sq::App holds the Telegraph, runs the model at its far end, and holds the sq::Stage at its near one: the screens, the skin, drawing and input. You write two things, squared_main and your model; the platform layer (the Android template's entry.cpp) does the rest.

HeaderGives you
squared/stage/app.cppmsq::App, squared_main
squared/stage/module.cppmsq::Stage, sq::ScreenType, sq::CustomMaker
squared/stage/save.cppmsq::Save, sq::SavingModel: what a model keeps
squared/squared.cppmeverything an app is written against: the App, the Stage, the widgets and layouts, the Telegraph

Sprint 7.1, 7.2's C++ screens and custom nodes, 7.3's panes, 7.4's compiled-in skin, 7.5's bound values and lists, 7.6's kept screens and the model's save, and 7.7's internal host (ui() is no longer public: the widgets are the Stage's).

The shortest call site

#include <layouts.hpp>
import squared;

void squared_main( sq::App &app ) { app.stage.push( layouts::landing ); }

With a model:

void squared_main( sq::App &app )
{
    app.run<Prefs>();
    app.stage.push( layouts::landing );
}

layouts::landing is sq_app/layouts/landing.json, compiled by the build (layouts.md).

squared_main

void squared_main( sq::App &app );

Yours to write, in the global namespace. Called once, when the first window is up and the skin is loaded: push the first screen here, and start the model. Called again only after a quit, when the app starts afresh.

sq::App

One for the whole process. The platform makes it the first time and keeps it: when Android destroys the activity and makes another in the same process, the new one reattaches to the same App, the model keeps running, and the screens come back as they were. A new launch in that process (the app was swiped away from the recent apps, and Android kept nothing for it) starts fresh instead, as after a quit, unless the app keeps running in the background (Running in the background).

MemberDoes

run<M>( args... )start the model M, made from args on its own thread (named "model"). One model to an app: a second is refused, reported, and returns false
run<M>( sq::messaging::on_ui_thread, args... )the same model on the UI thread, one turn a frame: for tests and debugging

A model is a plain struct with receive, and optionally start, tick, background, foreground, low_memory (the model's page, messaging.md), and save (What is kept). The App calls them through the Telegraph:

AndroidThe model
leaving the screenbackground( telegraph ), then save( sq::Save & ) if it has one: it may never come back. A model on the UI thread takes that turn at once
coming backforeground( telegraph, elapsed ), elapsed in milliseconds, deep sleep included
short of memorylow_memory( telegraph )
a quitbackground, if it was not already, then it is destroyed on its thread

Quitting comes from app.quit() or a quit tap. The model saves and stops, and the stack is emptied; the next launch, even in the same process, runs squared_main again with a new Telegraph, holding nothing of the last run. Back at the first screen (by the back button or a back tap) does not quit: it sends the app to the background, as Home does (until 7.8 it quit).

The rest of App (create, handle_event, render, ...) is the platform's sq::app::Application (app.md): the platform calls it, an app does not.

Running in the background

For a model whose work goes on with the app off the screen: a shell, a download, a long build. Android otherwise freezes a cached app's processes soon after it leaves the screen, and may end them.

void squared_main( sq::App &app )
{
    app.run<Shell>();
    app.keep_running( { .title = "sqterm", .text = "1 session" } );
    app.stage.push<Terminal>();
}
While it runs
the notificationthe title and text (each at most 63 bytes of UTF-8, cut at a character); tapped, it opens the app. Called again, the text changes
Exit (in it)the app gets QuitRequested, a quit: the model saves and stops, the service with it
Acquire / Release wakelock (in it)the CPU stays on with the screen off, until released or the service stops: the platform's own, the app is not told
a swipe from the recent appsthe activity goes, the process and the model stay; the app opened again comes back to them (not a new launch)
a quit, or stop_running()the notification goes, and the wake lock

On Android it needs BACKGROUND=1 in the app's Makefile (the service is squared's dev.squared.ModelService; the template's sq_android/README.md). Without it, or on a host build, keep_running returns false and does nothing else. Failure modes: false from keep_running; Android 13 and later ask for the notification permission the first time, and without it the service still runs with its notification hidden. Not bound to Lua.

sq::Stage

A stack of screens, each a layout. Only the top one has widgets; a screen that comes back (back) is built again from its layout, and what it kept when it was left is put back: where its lists and scroll panes were, and an edit not finished (What is kept).

A layout passed to push or replace must outlive its place on the stack: a compiled one (layouts::settings) is a constant, so it always does.

C++ screens

What a layout file cannot say, a screen written in C++ can: a type with a name and a build, no object (sq::ScreenType checks it):

struct About {
    static constexpr std::string_view name = "about";
    static void build( sq::gui::LayoutWriter &root )
    {
        root.add<sq::gui::Label>( "this screen is written in C++" );
        root.row();
        root.add<sq::gui::Button>( "Back" ).tap( sq::gui::Navigate::back );
    }
};

app.stage.push<About>();

build writes the same table a layout file compiles to (layouts.md), and runs each time the screen is shown, so it keeps nothing between showings: values come from the model. It writes into a scratch the Stage keeps per window, scratch_nodes (256) nodes, scratch_text (8 KB) of text and scratch_numbers (256) numbers; a screen that writes more shows what fit, and is reported.

To reach it by name, from a layout file's push about or another screen's tap, add it in squared_main, and list it in names.json's screens (sqgen checks a layout's targets against the files and that list):

void squared_main( sq::App &app )
{
    app.stage.add<About>();
    app.stage.push( layouts::landing );
}

At start the Stage reports each screen names.json lists that was not added. In C++, a tap can name the type instead: .tap<About>( sq::gui::Navigate::push ) writes push about, checked when it compiles.

Panes

A pane is a layout over the screen shown: a question, a menu, a drawer. In a file it is "kind": "pane", with two keys of its own (layouts.md):

{ "kind": "pane", "place": "bottom", "modal": true, "rows": [
  [ { "type": "label", "text": "Quit?", "span": 2 } ],
  [ { "type": "button", "text": "Yes", "tap": "quit" },
    { "type": "button", "text": "No", "tap": "close" } ] ] }

A screen's button opens it, "tap": "open quit"; in C++, app.stage.open( layouts::quit ). A button in it closes it, "tap": "close", as does back.

placeWhere
center (the default)the middle, at the size it asks for
left, rightthat edge, the screen's height
top, bottomthat edge, the screen's width

Always inside the safe area, and never bigger than it. Modal (true; the default is false): the screen dims and takes no taps until the pane closes. Not modal: a tap outside the pane reaches the screen. A pane opened over a modal pane is modal too, since nothing beneath a modal pane takes taps. A pane is drawn in the skin's pane frame (its pane window style, on default-pane): no title bar, no close button; a tap on the frame between its widgets stays in the pane.

A C++ screen opens as a pane too, open<About>() or open about (when it is added); two constants, both optional, give its place and modal:

struct Ask {
    static constexpr std::string_view name = "ask";
    static constexpr sq::gui::PanePlace place = sq::gui::PanePlace::bottom;
    static constexpr bool modal = true;
    static void build( sq::gui::LayoutWriter &root );
};

A pane belongs to its screen. Up to max_panes (4) are open at once; the last opened is on top. Leaving the screen (a push, a replace, a back to the screen beneath) closes them, and they do not come back with it. A pane is built when it opens and freed when it closes, so a pane opened again starts afresh: its values come from the model. A window made again (Android recreating the activity) builds the screen and its open panes again.

Bound values

A node with a bind (layouts.md) shows a value the model states, and a node that edits sends what the user does:

// The model: a key that carries state and set.
constexpr sq::messaging::Key<double, sq::messaging::state | sq::messaging::set> volume{
    "settings.volume" };

// The screen: a slider that sets it, and a label that shows it.
root.add<sq::gui::Slider>().range( 0.0F, 10.0F ).bind( volume );
root.add<sq::gui::Label>( "-" ).bind( volume );

In a layout file, "bind": "settings.volume", with the address in names.json. Nothing else to write: the Stage keeps the value in the Telegraph's cache while it is shown, and shows each new one the frame it comes.

NodeShowsSends, when the key carries set
labelany value but a uid list, as the text form writes it (2.0, ann, true)nothing
check_boxa boolset with the new state, at once
slidera number or an integerset, once a frame while dragged: the last place; an integer key gets the nearest whole number
text_fieldtextset with the text, when the edit is finished: Done (Enter), or leaving the field after changing it
progress_bara number or an integernothing

Until the model says, a widget shows what the layout gave it (a label its text). A pane opened later shows the latest value at once.

While the user holds it (a slider being dragged, a text field with the focus), what the model says is not shown on it, so a finger is never fought; the other widgets bound to the same value show it, and the held one does when it is let go. What the model answers to a widget's own set is shown, and not sent back.

A value of another type than the key's (the model's key and names.json disagree) is not shown; the build refuses the mismatches it can see (a check_box bound to a number, a text_field to a bool).

Up to max_bindings (128) widgets are bound at once, a screen's and its panes', a list's rows' among them; past that the rest show their own text, and it is reported once. Leaving a screen, or closing a pane, unbinds its widgets.

A widget whose value changed is laid out again before the frame is drawn: a longer text takes its room. A frame where nothing changed lays out nothing.

Bound lists

A list node shows one of the model's lists (names.json's "inventory": { "list": "item" }), however long: widgets are made only for the rows on screen, and reused as it scrolls. Its row is one node, built once for each row on screen; in it, an address that takes a uid gets the uid of the row's item:

// The model: the list, and an item's values by its uid.
t.list( names::inventory, inventory );        // count(), uid_at( row ), publish( t, uid )
t.state( names::item_name, 17, "fur coat" );

// The screen: each row the item's name, and a button that sends `do item.use` to it.
auto row = root.add_list( names::inventory ).grow().add<sq::gui::Table>();
row.add<sq::gui::Label>().bind( names::item_name );
row.add<sq::gui::Button>( "Use" ).tap( names::item_use );

In a layout file:

{ "type": "list", "bind": "inventory", "grow": true, "row":
  { "type": "table", "rows": [ [
    { "type": "label", "bind": "item.name" },
    { "type": "button", "text": "Use", "tap": "do item.use" } ] ] } }

The model gets do item.use with the row's item as its uid (received.telegram.address().uid), and a check box, slider or text field in a row sends set to its item the same way. The row's own addresses (settings.sound) and navigation taps work as anywhere.

WhatHow

Up to max_lists (4) lists are shown at once, a screen's and its panes'; past that the rest stay empty, and it is reported. The model keeps one view of a list, so one widget shows it: a second (in a pane over the screen showing it) stays empty, and it is reported. A row shows up to max_row_values (8) of its item's values; one list in a row is refused (one level, for now).

What is kept

A screen keeps where it was. While a screen is not built (beneath the top, or with no window), the Stage keeps, for it and for each open pane:

WhatHow much
where its lists and scroll panes were scrolledthe first kept_scrolls (4), in the layout's order; a list's rows are not counted
an edit not finished (typed, no Done, not left)the first text field that has one, up to kept_text (128) bytes, cut where a character starts

It is put back when the screen is built again: back to it, a window made again, a lost context. A list's place comes back once the model has sent its count again (the rows reach it). An edit put back is the user's still: it is sent on Done, or on leaving the field, and what the model says meanwhile waits, as for a field with the focus.

The stack outlives the process, when Android brings the app back. When Android asks what to keep with the activity (its saved instance state), the App gives it the stack, the panes over the top, and what each keeps: a few hundred bytes, held by Android, not in the app's files. Android hands them back only when it ended the process itself (for memory, or the freezer) and the user returns to the app; then, after squared_main, the stack is shown again as it was. A swipe from the recent apps, a quit, a force stop or a reboot gives nothing back: the app starts fresh at squared_main's screen (decided 2026-10-27). A swipe that leaves the process alive starts fresh as well: the App stops the model, which saved when the app left the screen, and runs squared_main again. Each screen is found again by its name, so every screen on the stack must be a layout file or an added C++ screen; one that is not (a layout pushed that layouts::all() does not list) keeps nothing, and it is reported.

void squared_main( sq::App &app )
{
    app.stage.keep_screens( false ); // start at the landing screen, always
    app.stage.push( layouts::landing );
}

Until 7.8 the stack was a file, squared/screens, and a swipe from the recent apps kept it too. The App removes a file left from then at its first start.

A model keeps its own values with a save: called after each background (a quit's too), on the model's thread, it writes the values to keep with sq::Save::state, as the Telegraph's state takes them:

struct Hello {
    bool sound = true;
    double volume = 5.0;

    void receive( sq::messaging::Telegraph &t, const sq::messaging::Received &m );  // takes the sets

    void save( sq::Save &save )
    {
        save.state( names::settings_sound, sound );
        save.state( names::settings_volume, volume );
    }
};

Each is kept as a set line (set settings.volume 5.0) in squared/model.state. At the next start, before start, each comes back to receive as the UI's set would: what receive already does with the Settings screen's sets is all it takes to read them. A key must carry set to be saved (a key without it does not compile); a key with a uid takes it: save.state( item_kept, 17, true ). A save holds sq::Save::capacity (8 KB); one that does not fit is not written, and the last stays. The file is the model's: a quit keeps it.

Custom nodes

A layout's "type": "custom" node (add_custom( "minimap" ) in C++) is made by a function the app gives:

std::unique_ptr<sq::gui::Widget> make_minimap( sq::Stage &stage )
{
    return std::make_unique<Minimap>( stage.telegraph() );
}

app.stage.custom( "minimap", make_minimap );

The maker is given the Stage (12.3d): its telegraph() is what the widget reads the model's values and snapshots from and sends to, and its navigation is what a tap inside the widget may push or open. A plain function pointer, so a lambda with no capture does too.

A custom node with no maker shows a label saying so, and is reported.

Navigation asked for while an event is being delivered waits until delivery has finished: a tap's push settings is applied after the tap, since building the next screen replaces the widgets, the tapped button among them. Up to four navigations can wait for one event; more are dropped and reported.

The clipboard

stage.clipboard() is the platform's clipboard (sq::app::ClipboardService, app.md): what a paste reads and a copy writes, for a custom widget (sqterm's terminal). nullptr where the platform gives none (a host test), and between one activity's end and the next's start, so a widget asks each time rather than keeping it.

if( sq::app::ClipboardService *clipboard = stage_.clipboard() ) {
    clipboard->set_text( selected );
}

Zoom: the pinch

Every squared app zooms with two fingers, as Termux does (12.6b): spread them and the whole UI grows, pinch them and it shrinks, from 50% to 300% in steps of 5. Nothing to write for it. The zoom is how many logical units the shorter side has: 720 at 100%, 360 at 200%, so every widget, its text and its touch area grow together, and the layout fills the screen again. It is laid out once a step, not once a frame, so a pinch costs a layout every 5% and nothing between. Kept in the app's private files (squared/zoom, a number and a newline), written as the fingers lift; the next launch starts there.

How a pinch reads: the second finger down starts it, and the first finger's press is cancelled (a button under it is not clicked; a drag stops). The fingers must move apart or together by 2.5% of the shorter side before it zooms, so two fingers that land and lift change nothing. From there the scale counts from where they were. Until every finger is up, none of them reach the widgets; a third is ignored (in a CONSOLE build three fingers are the Console's, which ends the pinch where it was).

A widget may take the pinch instead (gui::Widget::pinch, gui.md): the one under the fingers' middle is asked first, then its parents; one that says yes gets the pinch and the UI does not zoom. sqterm's terminal does, to scale its font.

app.stage.set_zoom( 150 );       // a settings screen's choice
app.stage.pinch_zoom( false );   // a game: two thumbs are two touches

The default skin's font is a bitmap drawn for 100%: at 300% it is scaled up, and softer. A widget that draws its own text (a terminal) draws it for the pixels it has (pixels_per_unit()), and stays sharp.

The window

The Stage draws in logical units: the drawable's shorter side is 720 (at 100% zoom, above), the longer one follows its shape, so a widget is the same size on every screen and a unit is square either way up. Touches arrive in pixels and are scaled once, here. The safe area (the bars over the screen's edges) is kept clear.

The skin comes with the framework: the default one, libGDX's uiskin, is compiled into the stage library, so an app ships no skin files and has nothing to load or say where. Its files are in the package at stage/skin/default/ (with their notice and the Apache License 2.0 they come under). One skin for now: an app's own comes later.

A rotation lays the screen out again, once, and builds nothing: its new size and its new safe area wait for the next frame (or the next touch, so a finger lands where the widgets are), and are laid out together. A list taller than it was builds a row's widgets for each row it now shows.

The system bars are hidden (immersive), on Android: the whole screen is the app's, and a swipe from an edge shows the bars for a moment. A tool that wants them (an editor, where the keyboard and the bars should move the layout) says app.stage.hide_bars( false ), in squared_main or later; it takes effect at the next frame. The safe area is what still covers the window: a camera cut-out, the keyboard, the bars while shown.

Short of memory, Android's onLowMemory: screens beneath the top hold no widgets already; the Stage frees the working sizes every table's layout keeps warm (made again at the next layout), and the model hears of it.

Memory

The App is made once, in static storage, not on the heap: the Telegraph line (88,576 bytes at the default sizes, which its knobs set) and 4,288 bytes more (the Stage is 4,088: its stack, the added screens and custom types, the pane slots, and 2,960 bytes of what 16 screens and 4 panes keep), and the two paths where it keeps things (allocated once, at start). The skin's files are 46 KB of read-only data in the program, mapped from its file, not the heap. A model's runner is one allocation, at run. Each window allocates the skin's textures and tables (reading them copies each file once, briefly) and one block of about 24 KB (on Android 23,976 bytes: batch, camera, painter, widgets, the fingers a pinch follows, the 17 KB scratch C++ screens and panes write into, the 4 KB table of bound widgets and 640 bytes for the lists); each screen shown allocates its widgets, and each pane opened its frame (168 bytes) and widgets, freed when it closes. A list shown allocates its row's copy and, as it is first laid out, a row's widgets for each row on screen and one more, and 4 bytes a row it asks for. A C++ screen itself allocates nothing. A frame allocates nothing, a list scrolling included, once each part of the screen has been laid out once.

A pinch allocates nothing: the zoom is a byte of the Stage, the fingers are in the window's block, and the zoom's file is read once a process (a few bytes, briefly) and written from the stack.

Keeping: the background writes the stack from an 8 KB buffer on the stack; a model's save writes into one on its thread's stack; the model's last save is read into one allocation at run and freed once given back.
