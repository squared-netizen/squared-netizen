Building

squared builds with clang and GNU make. No CMake, no generator step, no network access, and nothing that assumes a desktop. squared is modules, in C++23 (include-layout.md), which it builds the way clang does: CXX is clang++ by default, and another compiler stops the build at once. On Termux, g++ and c++ are clang already. The standard library is libc++, everywhere: Android's and Termux's already; on a desktop, install it (Debian and Ubuntu: apt install libc++-dev libc++abi-dev).

Desktop Linux and Termux

./tools/build.sh              # release
./tools/build.sh debug        # -O0 -g
./tools/build.sh release -j4  # extra arguments go to make

Or drive make directly:

make                 # every module
make gui             # one module
make BUILD=debug
make headers         # the pinned std sources, the modules' build order
make sqgen           # sqgen and sqconsole, for this machine, in build/<BUILD>/
make test            # every module's tests, each only if it changed (below)
make retest          # every test again
make clean

Archives land in build/<release|debug>/lib/libsquared_<module>.a.

What a build prints. One short line as each step starts, and the flags once:

squared release: flags as before
  mod  sq.messaging-telegram
  cc   messaging/src/telegram.cpp
  ar   libsquared_messaging.a
  bin  messaging/telegram_test
  test messaging/telegram_test
       ok
  gui: 4 unchanged since they passed

cc compiles one file (its path from squared/), ar makes a module's archive, bin builds a test or tool, and test runs one: ok or FAIL is the line after. The first line says the flags are what they were; when they are not (another CXX, SQUARED_ABI, BUILD's optimisation, or a first build) it lists every flag, one to a line, marking each (new) or (gone), and everything they affect is rebuilt. Warnings and errors print in full, as the compiler wrote them. A failed test prints its whole output after FAIL; a passing test's output is in build/<release|debug>/<test>.log.

make V=1             # every command, and every test's output, in full

Tests run only when something they cover changed. A test binary is rebuilt when its sources, the archives it links, the files and module interfaces it reads or the flags change, and make test runs it only when it was rebuilt since it last passed. A module whose tests were all kept says how many: gui: 4 unchanged since they passed. With nothing changed make test takes about a second; make retest (or make test RETEST=1) runs all of them. A failed test is run again next time, changed or not.

Modules outside this tree

Every squared module is in this tree, and so is the one third-party dependency. Unpack it once after checkout:

./tools/vendor_third_party.sh

That reads third_party/yyjson-*.tar.gz and puts yyjson.c and yyjson.h in third_party/yyjson/. It is idempotent, and it leaves an already-unpacked dependency alone, so it is safe to re-run and safe to delete the tarball afterwards.

data/Makefile compiles yyjson.c into libsquared_data.a, so an application links one library rather than two, and local.mk is not needed for it.

Why vendored rather than a system package. This tree is built with the NDK toolchain for an APK. pkg install yyjson under Termux gives you a header and a library built for the host sysroot &mdash; the wrong target. It may even link and then fail on a device. The source is compiled by your build, for your target, or not at all.

local.mk still exists for anything else you need on the include path, and is still picked up automatically.

build/common.mk picks it up automatically. local.mk is per-checkout and should not be committed. Setting the variable on the command line still works for a one-off:

SQUARED_EXTERNAL_INCLUDES="-I../application/include" ./tools/build.sh

For Android

A project made from the Android template builds squared for you, for the project's target: make in the project compiles the vendored squared/ with the same compiler, API level and NDK sysroot as your own code. You do not build the framework separately.

The API level is SQ_MIN_SDK in the project's mk/squared_generated.mk, default 22 (Android 5.1). It is what the code is compiled and linked for, not only what the manifest claims, so one APK runs on Android 5.1 and on every release after it.

make apk                  # for API 22
make apk SQ_MIN_SDK=26    # for Android 8.0 and later only
make android-status       # the NDK, the API level, the C++ runtime it found
What happensWhy
A call to a function newer than SQ_MIN_SDK fails the linkIt is not in that level's system libraries; reach it with dlsym and do without when it is absent
The C++ runtime is linked into your libraryOne .so, nothing beside it to get out of step; the APK carries no libc++_shared.so
The link fails if the library could not load on Android before 6.0It must carry the DT_HASH symbol table; the build adds it
Changing SQ_MIN_SDK or the NDK rebuilds the frameworkArchives built for one level must not link into another
CONSOLE=app (or monitor) links the Console in; the default, 0, carries none of itSee console.md. Switching it rebuilds nothing in the framework: its Console archive is built every time and only linked when asked for
TELEGRAPH_RING=512 (or another TELEGRAPH_*) sizes the Telegraph; unset ones keep their defaultsThe app and the framework are built with the same ones, since the app makes the line; changing one rebuilds both. See messaging.md
DEV_LOG and CONSOLE builds are debuggable; plain builds never arerun-as reaches a debuggable app's private files; SQ_DEBUGGABLE= turns it off, SQ_DEBUGGABLE=1 on
make install uses adb install -r when adb reaches this phone, and Android's installer otherwiseNo prompt with adb; a second device (a tablet) only when named, DEVICE=<serial>

The NDK must have libraries for the level you ask for; make says which levels it has if not. NDK r29 has 21 to 35.

The SDK's own toolchain

The framework also builds for Android with the SDK's own toolchain: clang 23, libc++ 23 and bionic, from sqterm's llvm, runtimes and sysroot packages (on CI, apt.llvm.org's clang 23 with the same two packages). No NDK is involved ("One C++23 toolchain", phase 3; the template moves in phase 4).

make SQ_TOOLCHAIN=1       # in squared/: build/toolchain.mk's compilers and flags

build/toolchain.sh finds the packages under $PREFIX. On another machine, name them with SQ_LLVM_BIN, SQ_SYSROOT and SQ_RUNTIMES. The build goes in build/<BUILD>-<fingerprint>/, so its modules never meet another toolchain's.

Installing, starting, the log

make install      # adb install -r on this phone when adb reaches it, else the installer
make run          # install, then start it (adb)
make logcat       # the app's lines, a library that failed to load, the crash summary (adb)
make devices      # what adb reaches, which is this phone, and how to connect
make dev          # the build you debug with: CONSOLE=app DEV_LOG=1 install
make console      # a CONSOLE build's Console in this terminal, no adb (see console.md)
make console-only # start it with only the Console running

On the phone itself adb comes from Termux's android-tools and Wireless Debugging (Android 11 and later, on Wi-Fi): pair once, then connect each time it is turned on. The project's README walks through it. Without adb, make install hands the APK to Android's installer, as before, and Termux cannot read the app's log at all; the dev log (DEV_LOG, dev.md) and the Console (console.md) work without either.

Flags

build/common.mk holds every shared setting and each one is overridable:

make CXX=clang++ BUILD=debug CXXFLAGS_EXTRA=-fsanitize=address

Defaults are -std=c++23 -stdlib=libc++ -O2 -Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wsign-conversion, plus -ffunction-sections -fdata-sections -fvisibility=hidden so the linker can drop what an application does not use. The tree builds warning-free at that level.

Every module is compiled before what imports it (7b.4): mod sq.gui-label is an interface becoming its BMI, in build/<BUILD>/modules/. The standard library is a module too, std (C++23; built from libc++'s own sources, those of the libc++ installed), made first, and only once for each compiler, flag set and libc++ on the device: in ~/sqsysroot/.sqpg/std/ when squared-pg is set up, shared by every project (mod std (libc++ 210000, made before: ...) when another project made it), else in the build. Every file reads from it only what it uses. A new libc++ makes a new std module, with nothing to pin. (Until 7b.4 the standard headers were precompiled; until 2026-11-02 squared had its own module of them, sq.std.)

A test is rebuilt only when something it includes changes, and the objects of the sources tests share are kept in build/<BUILD>/test-objects/ and reused.

Framework objects are cached (7b.3), by what each compile reads: the source and every file it includes by content, the module interfaces it may import, the compiler and the flags. Module interfaces are cached the same way, their BMI kept with the object. A compile that would read the same again takes the object instead: a new workspace (it compiles nothing that another workspace on the device already did), a make clean, a header edited and edited back. With squared-pg set up the cache is one for every workspace on the device, ~/sqsysroot/.sqpg/cache; otherwise it is the workspace's build/cache, which make clean keeps. The archive's line says how many came from it:

  ar   libsquared_gui.a (39 from the cache)

It is kept under 500 MB, least lately used out first:

make SQUARED_CACHE_SIZE=2000    # megabytes
make SQUARED_CACHE=off          # compile everything, keep nothing
make SQUARED_CACHE=/elsewhere   # another cache

So that one workspace's objects suit another, paths in objects start at squared/ (-ffile-prefix-map): a debugger finds the sources when started from the directory that holds squared/.

SQUARED_ABI carries -fno-rtti, which builds and passes every test (make SQUARED_ABI=-fno-rtti test); -fno-exceptions does not build yet. See [../developer/build-and-toolchain.md]( ../developer/build-and-toolchain.md).
