messaging

The Telegraph's parts: names and addresses, keys, the 32-byte telegram and its one line of text, the ring that carries telegrams from one thread to another, the latest-value cache, both ends of a virtualized list, and the Telegraph that joins them, with the runner that gives the model its own thread. This page grows with the Telegraph.

Every type below lives in its own header. Include exactly the ones a translation unit names; squared/messaging/module.cppm pulls in all of them and exists for convenience, not for use inside headers of your own.

Developer counterpart: ../developer/messaging.md

[!note] The old dispatcher is gone (2026-10-20) MessageDispatcher, EndpointId, MessageId, the JSON-payload Telegram and the providers were removed: nothing used them, and the app model replaces them. Scheduled delivery became the model's timers (sq::time::DeadlineQueue).

Names and addresses

A telegram goes to an address: a name, which is the schema (player.hp, item.name, inventory), and a uid, which says which object (the model's own id for an item, a buffer, a row). Names are written in the code; uids come from the data.

import sq.messaging;

using sq::messaging::Address;
Address hp{ "player.hp" };              // no uid
Address coat{ "item.name", 17 };        // item[17].name
TypeHeaderIs
Namesquared/messaging/name.cppm8 bytes: the 64-bit FNV-1a hash of the name's text
Addresssquared/messaging/address.cppma Name and a 32-bit uid (0: none); 16 bytes
NameTablesquared/messaging/name_table.cppmthe registered names' text, for writing telegrams as text

A name literal costs nothing at run time. Name n = "player.hp"; is hashed by the compiler, and checked there: a name is dot-separated segments of a-z, 0-9 and _, at most 255 bytes, so Name n = "Player HP"; does not compile. A name built at run time (from a mod's file, say) is Name::of(text): hashed once, and checked when it is registered.

Data never goes in a name. Which item is the uid, how many is the value. Names are a few hundred, or a few thousand with mods; that is what keeps the name table small and the ids from colliding.

The text form

AddressWritten
{ "player.hp" }player.hp
{ "item.name", 17 }item[17].name: the uid after the first segment
{ "inventory", 20 }inventory[20]
a name not registered, uid 3# and the id's 16 hex digits, then [3]

parse_address(text) reads that back with no table (the name is hashed):

if( auto address = sq::messaging::parse_address( "item[17].name" ) ) {
    // address->name == Name("item.name"), address->uid == 17
}

It returns nothing for text that is not an address: an invalid name, a uid past 4,294,967,295, brackets anywhere but after the first segment. [0] reads as no uid.

The name table

std::array<std::byte, 8192> storage;           // the Telegraph will own this
sq::messaging::NameTable names{ storage };
names.add( "player.hp" );                      // added
std::array<char, 64> line;
std::size_t n = names.format( { "item.name", 17 }, line );  // "item[17].name"
CallDoes

16 bytes per name plus its text: 8 KB holds about 250 names. Nothing allocates; the storage is yours (the Telegraph's, later) and must outlive the table. Register names before the threads start.

Keys

Every address in an app is a key: a name with the type of its value, the verbs it carries, and whether it takes a uid.

import sq.messaging;

namespace names {
using namespace sq::messaging;
inline constexpr Key<std::int64_t, state>                  counter_ticks{ "counter.ticks" };
inline constexpr Key<bool, state | set>                    settings_sound{ "settings.sound" };
inline constexpr Key<std::string_view, do_>                file_open{ "file.open" };
inline constexpr Key<void, event>                          game_over{ "game.over" };
inline constexpr Key<std::string_view, state, with_uid>    item_name{ "item.name" };
}

Write them by hand in a header, or let names.json generate them (Sprint 9e): the same type either way. A dot in the name becomes an underscore in the identifier.

The compiler checks every send against the key. The Telegraph's calls are constrained by sendable<Key, Verb, Value>, so these do not compile:

A key is 16 bytes: the name (8) and a pointer to its text (8), for the name table. Keys are constants; a telegram carries only the 8-byte name.

The telegram

sq::messaging::Telegram (squared/messaging/telegram.cppm) is one message, 32 bytes: the name, the uid, a correlation (which pairs a do with the event that answers it, 0 for none), the verb and value type, and 16 bytes of value. Apps send through the Telegraph with keys; this is what travels underneath, and what a replay file or a test makes by hand.

using namespace sq::messaging;
const Telegram ticks = Telegram::integer( Verb::state, { "counter.ticks" }, 42 );
const Telegram open  = Telegram::data( Verb::do_, { "file.open" }, ValueType::text, where )
                           .with_correlation( 12 );
FactoryValue
empty(verb, to)none
boolean(verb, to, b)a bool
integer(verb, to, i)a 64-bit integer
number(verb, to, d)a double; not a NaN (asserted: a NaN has no text form)
floats(verb, to, span)two to four floats; no NaN
data(verb, to, type, where)text or a uid list, by where it is in the data area (DataRef: offset and length in bytes, 4 per uid)

Read it with verb(), type(), address(), correlation(), and as_boolean(), as_integer(), as_number(), as_floats(), as_data() for its type. with_correlation(c) and with_uid(uid) make the same telegram answering c, or to another uid of its address (a list row's item). valid() says whether 32 bytes that came from elsewhere (TelegramBytes::from) are a telegram; the factories only make valid ones, with every byte a value does not use zero, so equal telegrams are equal byte for byte.

read_telegram needs no name table: names are hashed. It reads more than the canonical form (more spaces, [0], 1.50, 007), and writing what it read gives the canonical line. It refuses a NaN, an integer out of range, a correlation past 65,535, two to four floats only, and anything after the value.

TelegramData is a data area over storage you give it, filled from the front: append(bytes), at(where), bytes(), clear(). Nothing in this module allocates.

The ring

sq::messaging::TelegramRing (squared/messaging/telegram_ring.cppm) carries telegrams from one thread to one other, in order, with no lock and no allocation. The Telegraph runs one each way; an app sends through the Telegraph, not through a ring. A tool or a test that moves telegrams between two threads of its own can use one directly.

using namespace sq::messaging;
std::array<std::byte, 256 * 32> slots;   // 256 telegrams
std::array<std::byte, 8192> text;        // their text and uid lists
TelegramRing ring{ slots, text };

// the producer's thread
const std::string_view name = "notes.txt";
const Telegram open = Telegram::data( Verb::do_, { "file.open" }, ValueType::text, {} );
if( ring.push( open, std::as_bytes( std::span( name ) ) ) == RingResult::full ) { /* later */ }

// the consumer's thread
while( const auto got = ring.front() ) {
    handle( got->telegram, got->data ); // data: the text, valid until pop()
    ring.pop();
}

Exactly one thread pushes and exactly one reads. Neither ever waits: a full ring says so, an empty one has no front(). A uid list is 4 bytes a uid.

The latest-value cache

sq::messaging::ValueCache (squared/messaging/value_cache.cppm) keeps the last value of each address, so a screen built later shows current values at once. The Telegraph keeps one on the UI side and fills it from the model's state telegrams; an app reads it through its screens, not directly. A tool or a test can use one by itself.

using namespace sq::messaging;
std::array<std::byte, 512 * 32> entries;                      // 512 addresses
std::array<std::byte, ValueCache::index_bytes( 512 )> index;  // 2 KB
std::array<std::byte, 8192> text;                             // text over 16 bytes
ValueCache cache{ entries, index, text };

const Address name{ "item.name", 17 };
if( !cache.bind( name ) ) { /* every entry bound: a larger cache */ }   // a label shows it
const auto fur_coat = std::as_bytes( std::span( std::string_view( "fur coat" ) ) );
const Telegram state = Telegram::data( Verb::state, name, ValueType::text, {} );
if( cache.store( state, fur_coat ) != CacheResult::stored ) { /* counted in stats() */ }
if( const auto got = cache.find( name ) ) {
    show( got->data );                                // "fur coat", this frame only
}
cache.unbind( name );                                 // the label is gone: may be evicted
CallDoesFails with
ValueCache(entries, index, text)a cache over your storage: 32 bytes an entry, a power of two of them (2 to 32,768); index_bytes(n) of index; text may be emptyasserted: wrong sizes
store(telegram, data = {})makes the telegram's value the latest for its address; text and uids take their bytes from datadropped: no room (every entry bound, or the text area full of bound text), counted, and the address keeps its old value; too_large: over a quarter of the text area

  • What gets evicted: only addresses nothing is bound to, roughly oldest first, when room is needed.
  • Text from find lasts until the next store or bind (the cache may move it to make room). Use it within the frame; copy it to keep it.
  • Text up to 16 bytes lives in the entry and costs no text room.
  • One thread only. Nothing allocates.

The Telegraph

What a model sees: sq::messaging::Telegraph (squared/messaging/telegraph.cppm), its end of the line to the UI. It sends state and event by key, declares lists, and runs the model's side of a turn. The UI's end, TelegraphUi, is the Stage's; both live in one TelegraphLine, which the App owns (stage.md: app.run<Model>()), and a ModelRunner runs the model, on its own thread or the UI's.

namespace names {
inline constexpr Key<bool, state | set> sound{ "settings.sound" };
inline constexpr Key<std::int64_t, state> ticks{ "counter.ticks" };
inline constexpr Key<void, do_> reset{ "counter.reset" };
}

struct Counter {
    std::int64_t ticks = 0;
    bool sound = true;
    void start( Telegraph &t ) { t.state( names::ticks, ticks ); t.state( names::sound, sound ); }
    void receive( Telegraph &t, const Received &m ) {
        if( m.telegram.address().name == names::reset.name() ) t.state( names::ticks, ticks = 0 );
        if( m.telegram.address().name == names::sound.name() )
            t.state( names::sound, sound = m.telegram.as_boolean() );
    }
    void low_memory( Telegraph & ) {}            // optional, like background and foreground
};

auto line = std::make_unique<TelegraphLine>();  // about 86 KB, once
ModelRunner<Counter> runner( *line );            // Counter on its own thread, named "model"

TelegraphUi &ui = line->ui();                    // the Stage's end
ui.set( names::sound, false );                   // wakes the model
ui.do_( names::reset );
ui.drain();                                      // each frame: into the cache
std::optional<bool> sound = ui.value( names::sound );  // false, once the model has answered

(The App, Sprint 7, does all but the struct for you; a model writes only its struct.)

A model is any type with receive(Telegraph&, const Received&) (the TelegraphModel concept). Optional: start(Telegraph&), tick(Telegraph&, double seconds), low_memory(Telegraph&), background(Telegraph&), foreground(Telegraph&, std::uint64_t elapsed_ms), and for timers the pair wake_at() and due(Telegraph&, sq::time::TimePoint now) (see The model's thread). On a turn they come in a fixed order: low memory first; background and foreground in the order that ends where the app is now; quit last, after background (quit saves).

Sending mistakes do not compile: a verb the key does not carry, a value of the wrong type, a uid where the key takes none or none where it does.

SendResult: sent; pending (a state held back); full (no room: a set or do from the UI at once; from the model, an event, or a state when the pending table is full too, after its thread waited up to TELEGRAPH_WAIT_MS for the UI to drain); too_large (over a quarter of the data ring, never sendable).

The UI's end, TelegraphUi: set, do_ (returns the correlation), view (a list widget's rows), drain (states into the cache, then to a handler's state if it has one; events to its event), find and value (typed; text valid until the next drain), bind/unbind, and background, foreground(elapsed_ms), low_memory, quit for the model's next turn. It never waits. Each send wakes a sleeping model.

The Stage sleeps like this, when nothing is animating:

if( ui.ready_to_sleep() ) {
    pollfd fds[] = { { ui.wake_fd(), POLLIN, 0 }, /* input, ... */ };
    poll( fds, 2, -1 );
    ui.woke();
}
ui.drain( screens );

A handler's state is told of each state after the cache has it, so find already answers with the new value; the Stage shows bound widgets this way. Both members are optional, and drain() with no handler only caches:

struct Showing {
    void state( const sq::messaging::Received &received ) noexcept; // a value changed
    void event( const sq::messaging::Received &received ) noexcept; // an event came
};

A Received text's bytes are its data, all of it, from 0; the telegram's own DataRef is where it was in the ring, not in data.

Capacities are compile-time knobs, set as make variables in a project (-DSQUARED_TELEGRAPH_RING=512 in the build.lua flags; the framework and the app are built with the same ones) or -DSQUARED_TELEGRAPH_RING=512 by hand: TELEGRAPH_RING 256 telegrams each way, TELEGRAPH_DATA 8 KB of text each way, TELEGRAPH_PENDING 256 held states, TELEGRAPH_CACHE 512 values with TELEGRAPH_CACHE_TEXT 8 KB, TELEGRAPH_LISTS 16 of TELEGRAPH_LIST_VIEW 128 rows, TELEGRAPH_WAIT_MS 100 ms of waiting for room (0: never wait), TELEGRAPH_NAMES 8 KB of names for the dev tools (Console builds only: the table is theirs, not the line's), TELEGRAPH_SNAPSHOTS 4 snapshots (their buffers are not sized by a knob: they grow as the model needs), TELEGRAPH_WATCHES 4 watched descriptors. RING, DATA, PENDING and CACHE are powers of two; checked when the framework compiles. make status shows the ones set.

The model's thread

sq::messaging::ModelRunner<M> (squared/messaging/model_runner.cppm) runs a model at the model's end of a line.

ModelRunner<Shop> runner( *line, std::ref( database ) );   // its own thread
ModelRunner<Shop> runner( *line, on_ui_thread );           // or the UI's: runner.turn() each frame
CallDoes
ModelRunner<M>(line, args...)makes M from args on a new thread named model (the arguments are copied, as std::thread copies them: std::ref for a reference), calls start, then runs turns: deliver, then tick if due, then due if its time has come, then sleeps until the UI sends, a lifecycle signal, room for a held state, the next tick, or wake_at()
ModelRunner<M>(line, on_ui_thread, args...)makes M now, on the calling thread; nothing runs until turn()
turn()inline only: one turn, on the UI thread (ticks and timers that are due run in it); the telegrams handled, 0 once the model has quit
threaded()whether the model has its own thread
~ModelRunner()asks the model to quit (it saves: background if the app was visible), wakes it, and waits for it to end; M is destroyed on the thread it lived on

Preconditions: one runner to a line, and the line outlives the runner. A line serves one model: after its runner is gone it keeps that model's quit and values, so a second model needs a new line (the App makes one after a quit). The model's thread never touches the UI's end, nor the UI the model; on its own thread the model is not reachable from the UI at all. Failure modes: none returned; a thread the system cannot make ends the program at start.

Waiting for room. On its own thread, a model whose event finds the ring full, or whose state finds the pending table full too, waits up to TELEGRAPH_WAIT_MS (100 ms) for the UI to drain, then gets full. Inline, the UI cannot drain meanwhile, so full comes at once. A quit ends a wait at once. Both are counted in wait_stats(), which the telegraph Console command (6.7) will show.

Ticks run on the model's thread at the interval tick_every asked for, measured by a sq::time::Timepiece (see time.md): seconds is the time since the last tick, at most 0.25, and the first tick measures from when tick_every was called. A model that fell behind starts the cadence again rather than catching up in a burst.

Timers. A model with timers says when it next needs a turn, and is called when that time comes; it sleeps in between, ticking or not. Most keep a sq::time::DeadlineQueue:

std::optional<sq::time::TimePoint> wake_at() const { return timers.next_due(); }
void due( Telegraph &t, sq::time::TimePoint now ) {
    timers.poll_due( now, 16, [&]( Timer timer ) { fire( t, timer ); } );
}
HookCalled
wake_at()after each turn's deliver and tick: the time the model next needs a turn, or nothing. The thread sleeps no later than that
due(t, now)when that time has come, with the turn's one reading of the clock; then wake_at() is asked again

A model with wake_at() and no due does not compile. The clock is read once a turn, after deliver, for both the tick and the timers.

Watched descriptors (12.3d). A model that reads a pty, a socket or a pipe watches its descriptor, and is called when it has something to read or has closed; it sleeps in between, with no tick and no polling. sqterm's model reads its shell this way:

void start( Telegraph &t ) { t.watch( pty.fd() ); }
void readable( Telegraph &t, int fd ) {
    while( pty.read( buffer ) > 0 ) { /* ... */ }   // until it would block
}
Call or hookDoes
t.watch( fd )wake the model when fd is readable, closed or in error. True when watched (or already); false for a model with no readable, a negative fd, or TELEGRAPH_WATCHES (4) watched already
t.unwatch( fd )stop; nothing for one not watched. Before closing the descriptor
t.watching()how many are watched
readable( t, fd )in the next turn, after receive: fd has something to read, or has closed (a read gives 0 or EIO), or failed

The model owns the descriptor: the Telegraph only polls it, beside its own wake. A descriptor that closed stays ready, so readable unwatches it (or the model is called every turn). On its own thread, a model the UI keeps busy still hears from its descriptors: each turn looks at them. Inline, turn() looks at them once each frame. The runner forgets every watch when it ends.

A model made of parts

An app runs one model (App::run). One that does several things, a shell, a list of workspaces, an editor, can be several parts, each a model of its own in its own file, put together as one: sq::messaging::Composite<Parts...> (squared/messaging/composite.cppm).

struct Shell {
    static constexpr std::array takes{ term_input.name(), term_size.name() };
    explicit Shell( Places places );
    void start( Telegraph &t );
    void receive( Telegraph &t, const Received &r );
    void readable( Telegraph &t, int fd );
    bool watches( int fd ) const { return fd == pty_.fd(); }
};
struct Workspaces { static constexpr std::array takes{ ws_open.name(), ws_new.name() }; /* ... */ };
struct Editor { /* no takes: every name no other part takes */ };

using Model = sq::messaging::Composite<Shell, Workspaces, Editor>;
app.run<Model>( places, sq::messaging::no_args, sq::messaging::no_args );
A part hasWhat the composite does with it
receive (each part)a telegram goes to the part whose takes holds its name; a saved value too

Made in place. Composite<A, B, C>() makes each part with no arguments; Composite<A, B, C>( a, b, c ) makes each from its own, in order, sq::messaging::no_args for a part made with none. Parts are made where they live, so a part need not be movable (a pty, a thread's handle). They are made in order on the model's thread and destroyed in reverse. model.part<B>() reaches one by its type.

Costs: nothing allocated; a telegram is matched against each part's takes in turn (a few names each), and the hooks a part lacks are not called at all. Tested in messaging/test/composite_test.cpp.

Lists

A list of any length costs the UI only the rows on screen. The model holds the items; the list widget asks for the rows it shows, and the model sends those rows and their items' fields, nothing else. For a list named inventory:

What a model provides for a list (the ListRows concept): any object with three members. Uids are not 0.

struct Inventory {
    std::vector<Item> items;
    std::uint32_t count() const { return std::uint32_t( items.size() ); }
    std::uint32_t uid_at( std::uint32_t row ) const { return items[row].uid; }
    void publish( Out &t, std::uint32_t uid ) { /* t.state( names::item_name, uid, ... ) */ }
};

A type missing one of them does not compile. The Telegraph takes it as t.list( names::inventory, inventory ), and changes as t.changed( names::inventory ) (a sort, an insert, a removal) or t.changed( names::inventory, uid ) (one item's fields). The widget asks with ui.view( names::inventory, window ), the view travelling as two floats: do inventory.view (20 52), exact up to 16.7 million rows. Only what is on screen is ever sent: after a sort, the rows whose item changed, and the fields of items new to the screen; nothing for the rest of the list.

sq::messaging::ModelList (squared/messaging/model_list.cppm) is the model's end, sq::messaging::ListWindow (squared/messaging/list_window.cppm) the widget's. The Telegraph and the list widget use them; an app does not.

Snapshots

The third channel (12.3c): bulk state the model publishes whole, and the UI reads the newest of: a terminal's screen, a canvas's pixels. Not a telegram: it never goes through a ring, it is never coalesced or held back, and the UI never sees a half-written one. Each is named by a SnapshotKey.

inline constexpr sq::SnapshotKey screen{ "term.screen" };

// The model's thread:
const std::span<std::byte> room = t.snapshot( screen, bytes_needed );
write_into( room );
t.publish( screen, bytes_written );

// The UI thread, each frame:
if( const auto shot = ui.snapshot( screen ) ) {
    draw( shot->bytes );              // the newest; stays put until the next call
}
CallSideDoes
snapshot(key, bytes)modelroom for key, at least bytes, to fill; it grows (allocating, on the model's thread) only past every size asked for before; empty when TELEGRAPH_SNAPSHOTS keys exist already
publish(key, bytes)modelthe first bytes of that room are the newest; wakes the UI if it sleeps; false for a key never given room
snapshot(key)UIthe newest published, as SnapshotView: bytes, and sequence (1 for the first publish, counting each); the bytes stay as they are until the next call for key; nothing before the first publish

A snapshot is bytes: the model and the actor that draws it agree on what they mean (term::ScreenPublisher writes a terminal's screen, term::ScreenView reads it). The UI may skip publishes, so each must stand alone; the newest always arrives. Neither side ever waits. Three buffers a key, each as large as the largest snapshot written into it.

Dependencies

The standard library; time (the runner's Timepiece and clock); and POSIX as Linux and Android both have it: eventfd and poll for the wakes, pthread_setname_np for the thread's name. An app that uses ModelRunner links with -pthread (the project's make file does).
